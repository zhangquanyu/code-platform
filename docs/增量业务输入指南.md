# 4P12S 增量业务输入与迭代指南

## 问题背景

在实际项目中，业务输入很难一次性完成：

- **客户场景**: 客户今天想起一点，明天又想起一点
- **需求演化**: 初始需求模糊，随着讨论逐渐清晰
- **范围变化**: 业务方可能中途增加或删减需求
- **澄清反馈**: 需要多轮问答才能明确关键细节

**核心问题**:
1. 如何支持 2-3 步甚至更多步的业务输入？
2. 业务输入是否有约束规则？
3. 如何在增量输入时保持需求一致性？

---

## 4P12S 的增量输入支持机制

### 1. requirements 阶段的迭代设计

4p12s-requirements 技能天然支持增量输入，通过以下机制实现：

#### 1.1 需求登记表的增量更新

`requirements-register.md` 的设计支持增量更新：

```markdown
## 源需求登记

| 需求 ID | 类型 | 来源位置 | 原文摘录 | 结构化表述 | 优先级 | 验收提示 | 当前状态 |
|---------|------|----------|----------|------------|--------|----------|----------|
| BR-001 | BR | 第 1 轮输入 | "需要用户管理" | 提供用户注册、登录和管理能力 | 高 | ... | 已接受 |
| FUNC-001 | FUNC | 第 1 轮输入 | "用户可以注册" | 支持用户注册功能 | 高 | ... | 已接受 |
| FUNC-002 | FUNC | 第 2 轮输入 | "注册需要手机验证" | 注册时必须验证手机号 | 高 | ... | 已接受 |
| UI-001 | UI | 第 3 轮输入 | "注册页面要简洁" | 注册页面白色背景，顶部标题 | 中 | ... | 已接受 |
```

**关键点**:
- ✅ 每轮输入都有"来源位置"标记（如"第 1 轮输入"、"2026-08-17 补充"）
- ✅ 需求 ID 按类型递增，不重新编号
- ✅ "当前状态"字段跟踪需求接受状态

#### 1.2 澄清问题的迭代处理

```markdown
## 澄清问题

| 问题 ID | 关联需求 ID | 问题 | 影响 | 是否阻断 | 询问方式 | 状态 |
|---------|-------------|------|------|----------|----------|------|
| Q-001 | FUNC-002 | 手机号验证的具体规则？ | 影响 PRD 定义 | 是 | 直接提问 | 已回答 |
| Q-002 | UI-001 | 简洁的具体标准？ | 影响设计 | 否 | 提供选项 | 待回答 |
```

**澄清流程**:
```
第 1 轮输入
    ↓
登记需求（BR-001, FUNC-001）
    ↓
发现阻断问题 Q-001
    ↓
向用户提问 Q-001
    ↓
第 2 轮输入（回答 Q-001 + 新需求 FUNC-002）
    ↓
更新 Q-001 状态 + 登记 FUNC-002
    ↓
发现新问题 Q-002
    ↓
向用户提问 Q-002
    ↓
第 3 轮输入（回答 Q-002 + 新需求 UI-001）
    ↓
更新 Q-002 状态 + 登记 UI-001
    ↓
没有阻断问题 → passed
```

### 2. 增量输入的约束规则

#### 2.1 业务输入的格式约束（弱约束）

4P12S **不强制**业务输入的格式，但**建议**遵循以下规则：

**建议格式**:
```
【第 N 轮输入】

## 新增需求
1. <需求描述 1>
2. <需求描述 2>

## 补充说明
- 对 BR-001 的补充：...
- 对 FUNC-001 的修改：...

## 问题回答
- Q-001: <回答内容>

## 范围变更
- 新增范围：...
- 删除范围：...
```

**示例**:
```
【第 2 轮输入】

## 新增需求
1. 注册时需要手机号验证，验证码 5 分钟内有效
2. 注册页面要简洁美观，白色背景

## 补充说明
- 对 FUNC-001 的补充：注册支持手机号和邮箱两种方式
- 对 BR-001 的补充：主要面向 C 端用户

## 问题回答
- Q-001: 验证码有效期 5 分钟，最多重试 3 次

## 范围变更
- 删除范围：暂不支持第三方登录（原计划中的 FUNC-003）
```

#### 2.2 需求 ID 的稳定性约束（强约束）

**强约束规则**:
- ✅ 已有需求 ID 不得重新编号
- ✅ 同一前缀的新 ID 追加在当前最大编号之后
- ✅ 需求删除时保留 ID，标记为"已删除"
- ❌ 不要删除需求行（会导致 ID 断号）

**示例**:
```markdown
| 需求 ID | 类型 | 原文摘录 | 当前状态 | 备注 |
|---------|------|----------|----------|------|
| FUNC-001 | FUNC | 用户可以注册 | 已接受 | - |
| FUNC-002 | FUNC | 注册需要手机验证 | 已接受 | - |
| FUNC-003 | FUNC | 支持第三方登录 | 已删除 | 业务方明确暂不做 |
| FUNC-004 | FUNC | 支持邮箱注册 | 已接受 | 第 2 轮新增 |
```

#### 2.3 需求变更的追溯约束（强约束）

**强约束规则**:
- ✅ 需求变更必须记录"来源位置"
- ✅ 需求变更必须记录变更原因
- ✅ 需求变更必须评估对下游的影响
- ❌ 不要静默修改需求（不记录变更历史）

**变更历史记录**:
```markdown
## 需求变更历史

| 变更时间 | 需求 ID | 变更类型 | 变更内容 | 变更原因 | 影响评估 |
|----------|---------|----------|----------|----------|----------|
| 2026-08-17 | FUNC-001 | 补充 | 增加邮箱注册 | 业务方要求 | 需修改 PRD 验收标准 |
| 2026-08-18 | FUNC-003 | 删除 | 移除第三方登录 | 业务方暂不做 | 范围外增加说明 |
```

### 3. 增量输入的最佳实践

#### 3.1 分轮次输入的策略

**推荐策略**:

| 轮次 | 输入重点 | 产出 | 预计时间 |
|------|----------|------|----------|
| 第 1 轮 | 业务目标、核心功能、主要用户 | BR-xxx, FUNC-xxx (核心) | 30-60 分钟 |
| 第 2 轮 | 业务规则、数据字段、异常流程 | RULE-xxx, FIELD-xxx, FLOW-xxx | 30-60 分钟 |
| 第 3 轮 | 前端交互、非功能要求、外部依赖 | UI-xxx, NFR-xxx, INT-xxx | 30-60 分钟 |

**示例流程**:

```
第 1 轮输入（业务目标 + 核心功能）
    ↓
登记 BR-001, FUNC-001, FUNC-002
    ↓
生成澄清问题 Q-001, Q-002
    ↓
第 2 轮输入（回答 Q-001, Q-002 + 业务规则）
    ↓
登记 RULE-001, RULE-002, FIELD-001
    ↓
生成澄清问题 Q-003
    ↓
第 3 轮输入（回答 Q-003 + 前端交互）
    ↓
登记 UI-001, UI-002
    ↓
没有阻断问题 → passed → 进入 PRD 阶段
```

#### 3.2 增量输入的一致性检查

每轮输入后，执行以下一致性检查：

**检查清单**:
- ✅ 新需求与已有需求是否冲突？
- ✅ 新需求是否改变了已有需求的范围？
- ✅ 新需求是否引入了新的外部依赖？
- ✅ 新需求是否影响了已有澄清问题的答案？
- ✅ 需求优先级是否需要调整？

**示例**:
```
第 1 轮输入："注册仅需手机号"
    ↓
登记 FUNC-001: 手机号注册
    ↓
第 2 轮输入："还需要支持邮箱注册"
    ↓
一致性检查:
- ✅ 不冲突（邮箱注册是补充，不是替代）
- ⚠️ 范围变更：FUNC-001 需要修改为"支持手机号和邮箱注册"
- ✅ 无新外部依赖
- ✅ 不影响澄清问题
    ↓
更新 FUNC-001，新增 FUNC-002（邮箱注册）
```

#### 3.3 增量输入的阻断管理

**阻断问题分级**:

| 级别 | 说明 | 处理方式 | 示例 |
|------|------|----------|------|
| P0-阻断 | 必须回答才能继续 | 立即提问，等待回答 | "注册的具体流程是什么？" |
| P1-重要 | 影响 PRD 质量，但可以稍后回答 | 记录问题，可稍后回答 | "验证码的有效期是多久？" |
| P2-建议 | 不影响 PRD 生成 | 记录问题，可选回答 | "注册页面的按钮颜色？" |

**阻断问题合并策略**:
- ✅ 将多个 P0 问题合并为一次提问
- ✅ 按影响范围分组提问（业务流程组、数据规则组、前端交互组）
- ❌ 不要一次性提问所有问题（包括 P2）

**示例**:
```
第 1 轮输入后发现的阻断问题:
- Q-001 (P0): 注册流程包含哪些步骤？
- Q-002 (P0): 手机号验证的规则是什么？
- Q-003 (P1): 验证码有效期多久？
- Q-004 (P2): 注册页面按钮颜色？

合并提问策略:
第 2 轮提问: Q-001 + Q-002（P0 问题）
第 3 轮提问: Q-003（P1 问题，可选）
第 4 轮提问: Q-004（P2 问题，可选）
```

### 4. 增量输入的实战示例

#### 4.1 完整的多轮输入示例

**第 1 轮输入**:
```
我们需要一个用户管理功能：
1. 用户可以注册和登录
2. 管理员可以管理用户
```

**requirements 处理**:
```markdown
## 源需求登记（第 1 轮后）

| 需求 ID | 类型 | 原文摘录 | 结构化表述 | 状态 |
|---------|------|----------|------------|------|
| BR-001 | BR | "用户管理功能" | 提供用户注册、登录和管理能力 | 已接受 |
| FUNC-001 | FUNC | "用户可以注册和登录" | 支持用户注册和登录功能 | 已接受 |
| FUNC-002 | FUNC | "管理员可以管理用户" | 管理员可以查看、编辑、删除用户 | 已接受 |

## 澄清问题

| 问题 ID | 关联需求 ID | 问题 | 是否阻断 |
|---------|-------------|------|----------|
| Q-001 | FUNC-001 | 注册支持哪些方式？（手机号/邮箱/第三方） | 是 |
| Q-002 | FUNC-002 | 管理员具体可以管理哪些信息？ | 是 |
```

```
3. 注册页面要简洁美观
4. 性能要好，支持高并发
```

## 6. 常见问题解答

### Q1: 客户输入非常零散，如何整理？

**答**: 使用"输入来源表"记录每次输入：

```markdown
## 输入来源

| 时间 | 来源 | 内容摘要 | 整理人 |
|------|------|----------|--------|
| 2026-08-17 10:00 | 微信 | "需要用户管理" | 张三 |
| 2026-08-17 15:00 | 邮件 | 补充：支持手机号注册 | 张三 |
| 2026-08-18 09:00 | 会议 | 补充：管理员权限细化 | 李四 |
```

每轮输入后，整理到需求登记表中，保持需求 ID 稳定性。

### Q2: 客户中途大幅变更需求怎么办？

**答**: 使用"需求变更历史"记录：

```markdown
## 需求变更历史

| 变更时间 | 需求 ID | 变更类型 | 变更内容 | 变更原因 | 影响评估 |
|----------|---------|----------|----------|----------|----------|
| 2026-08-18 | FUNC-001 | 重大变更 | 手机号注册 → 邮箱注册 | 业务战略调整 | 需修改 PRD、US、design |
```

如果变更过大，建议：
1. 评估变更影响范围
2. 与业务方确认变更成本
3. 必要时重新初始化交付（新建 delivery）

### Q3: 如何判断增量输入可以结束？

**答**: 使用"阻断问题检查清单"：

```markdown
## 阻断问题检查（第 N 轮后）

- [ ] 所有 P0 问题都已回答
- [ ] 核心业务流程已明确（主流程、异常流程）
- [ ] 关键业务规则已明确（数据校验、权限规则）
- [ ] 核心功能范围已明确（范围内、范围外）
- [ ] 关键外部依赖已明确（上下游系统）

✅ 以上都满足 → 可以进入 PRD 阶段
❌ 有不满足 → 继续增量输入
```

### Q4: 增量输入时如何保持需求一致性？

**答**: 每轮输入后执行一致性检查：

```markdown
## 一致性检查（第 N 轮后）

- [ ] 新需求与已有需求是否冲突？
- [ ] 新需求是否改变了已有需求的范围？
- [ ] 新需求是否引入了新的外部依赖？
- [ ] 需求优先级是否需要调整？
- [ ] 已有澄清问题的答案是否需要更新？
```

### Q5: 业务输入是否有强制的格式约束？

**答**: **没有强制格式约束**，但建议遵循以下规则：

- ✅ 标记轮次（如"【第 2 轮输入】"）
- ✅ 区分新增、补充、变更、问题回答
- ✅ 引用已有需求 ID（如"对 FUNC-001 的补充"）
- ✅ 记录变更原因

4P12S 的 requirements 技能会自动整理零散的输入，转换为结构化的需求登记表。

## 7. 总结

### 增量输入的核心机制

| 机制 | 说明 | 实现方式 |
|------|------|----------|
| 需求 ID 稳定性 | 已有 ID 不重新编号 | 按类型递增 |
| 变更追溯 | 记录每次变更 | 变更历史表 |
| 澄清迭代 | 多轮问答 | 澄清问题表 |
| 一致性检查 | 每轮检查冲突 | 检查清单 |
| 版本管理 | 保留历史版本 | Git + 历史目录 |

### 最佳实践

1. **分轮次输入**: 按业务目标→业务规则→前端交互的顺序
2. **阻断问题分级**: P0 立即回答，P1/P2 可稍后
3. **变更追溯**: 记录每次变更的原因和影响
4. **一致性检查**: 每轮输入后检查冲突
5. **版本管理**: 使用 Git 保留历史版本

### 约束规则

**强约束**（必须遵守）:
- ✅ 需求 ID 不得重新编号
- ✅ 变更必须记录来源和原因
- ✅ 阻断问题必须回答才能进入 PRD

**弱约束**（建议遵守）:
- ✅ 标记输入轮次
- ✅ 区分新增、补充、变更
- ✅ 引用已有需求 ID
