# 4P12S 端到端交付技能体系分析

## 文档信息

- **分析对象**: 4P12S 端到端交付技能体系（12 个技能）
- **技能版本**: v1.0.3
- **分析时间**: 2026-08-17
- **文档路径**: `docs/4P12S 技能体系分析.md`

---

## 一、整体架构概览

### 1.1 技能体系定位

4P12S 是一套**端到端的软件交付流程技能体系**，覆盖从需求分析到发布触发的完整软件开发生命周期。该体系基于**渐进式交付**理念，将复杂的交付过程分解为 12 个可独立执行、可编排的技能节点。

```
原始业务需求
     ↓
[4p12s-delivery-orchestrator]  ← 初始化器
     ↓
[4p12s-requirements]           ← 需求登记与澄清
     ↓
[4p12s-prd]                    ← 产品需求文档生成
     ↓
[4p12s-user-stories]           ← 用户故事与验收场景
     ↓
[4p12s-technical-design]       ← 技术设计方案
     ↓
[4p12s-verification-plan]      ← 验证计划
     ↓
[4p12s-implementation-tasks]   ← 开发任务拆分
     ↓
[4p12s-implementation-execution] ← 开发任务执行（TDD）
     ↓
[4p12s-integration-test]       ← 集成测试验证
     ↓
[4p12s-e2e-test]               ← 端到端测试验证
     ↓
[4p12s-git-push]               ← Git 提交与推送
     ↓
[4p12s-deployment-execution]   ← 发布触发
     ↓
交付完成
```

### 1.2 核心设计理念

| 理念 | 说明 |
|------|------|
| **双模运行** | 每个技能支持编排模式（被 orchestrator 调用）和独立模式（用户直接调用） |
| **状态账本** | 通过 `delivery-state.md` 统一跟踪交付进度和阻塞原因 |
| **产物驱动** | 每个阶段产出标准化文档，作为下游阶段的输入契约 |
| **TDD 约束** | 实现阶段强制执行"红灯→实现→绿灯"的测试驱动开发流程 |
| **真实验证** | 集成测试和 E2E 测试阶段必须使用真实服务和真实接口断言 |
| **提交规范** | Git 提交信息必须符合 `commit-msg` hook 校验的格式模板 |
| **证据链** | 每个步骤的执行结果必须记录结构化证据，而非简单的"通过/失败" |

## 二、技能详细分析

### 2.1 4p12s-delivery-orchestrator（初始化器）

**职责**: 端到端交付系统的**初始化器**，仅负责创建交付状态账本。

**核心约束**:
- ❌ 不调用任何子技能
- ❌ 不执行任何 Step（需求、PRD、设计、实现等）
- ❌ 不进行任何验证、修复或回退
- ✅ 只做一件事：初始化 `delivery-state.md`

**输出产物**:
```
deliveries/<需求名>/
└── delivery-state.md
```

**状态账本结构**:
- 工作流元信息：workflow、delivery_name、workflow_status、current_step
- Step Checklist 表：跟踪 11 个阶段的完成状态和证据文件
- Task Checklist 表：记录开发任务的执行状态（由 implementation-tasks 填充）

**合法状态枚举**:
- Step/Task: `pending` | `running` | `passed` | `blocked` | `failed`
- workflow_status: `pending` | `running` | `blocked` | `failed` | `release_triggered`

**设计意图**: 分离初始化逻辑和流程编排逻辑，确保状态账本的唯一性和可信度。

---

### 2.2 4p12s-requirements（需求访谈与登记）

**职责**: 将原始业务输入转换为结构化的源需求登记，包含需求澄清流程。

**双模运行**:
- **编排模式**: 接收路径包，读取输入文件，写入 `requirements-register.md`
- **独立模式**: 自动发现项目根目录、入口文档，直接面向用户输出

**输出产物**: `requirements-register.md`

**需求 ID 规则**（稳定 ID 系统）:
| 前缀 | 类型 | 示例 |
|------|------|------|
| `BR-xxx` | 业务背景、目标、成功标准 | BR-001 |
| `FUNC-xxx` | 功能能力 | FUNC-001 |
| `RULE-xxx` | 业务规则、校验、风控策略 | RULE-001 |
| `FLOW-xxx` | 流程、状态流、异常路径 | FLOW-001 |
| `FIELD-xxx` | 字段、数据源、数据含义 | FIELD-001 |
| `UI-xxx` | 页面结构、交互、视觉风格 | UI-001 |
| `PERM-xxx` | 角色、权限、合规规则 | PERM-001 |
| `NFR-xxx` | 性能、安全、兼容性 | NFR-001 |
| `INT-xxx` | 上下游系统、API、事件 | INT-001 |

**澄清流程**:
1. 检查是否存在阻断 PRD 生成的澄清项
2. 合并阻断性问题，向用户提问
3. 用户回答后更新需求行和澄清行
4. 重新审计，直到没有阻断性澄清项

**质量门禁**（关键约束）:
- ✅ 每个文本或图片前端信号必须映射到 `UI-*`
- ❌ 禁止将前端交互信号降级为仅 `NFR-*`
- ❌ 文件中不得出现下游专属内容（US、AC、设计、实现结论）
- ❌ 澄清 ID（`Q-xxx`）不得替代源需求 ID

**返回状态**:
- `passed`: 登记有足够证据支撑 PRD 生成
- `blocked`: 存在阻断 PRD 生成的澄清问题且用户无法提供答案

**设计意图**: 建立需求追溯的源头，确保每个下游产物都能追溯到稳定的源需求 ID。

---

### 2.3 4p12s-prd（生成 PRD）

**职责**: 从已登记的业务需求生成产品需求文档，保留业务含义，不转为技术设计。

**前置依赖**: `requirements-register.md`

**输出产物**: `prd.md`

**核心章节**:
1. 背景与目标
2. 用户角色与场景
3. 功能范围（范围内/范围外）
4. 业务流程（主流程、异常流程、边界流程）
5. 业务规则
6. 字段、数据与状态口径
7. 系统边界与外部依赖
8. 非功能要求
9. 验收标准
10. 待确认问题

**映射规则**:
- ✅ 范围内的每个需求 ID 必须出现在 PRD 中，或在 `范围外` 中附带原因
- ✅ 每个范围内的 `UI-*` 需求必须出现在用户角色/场景、流程和验收标准中
- ❌ 除非 `requirements-register.md` 明确排除前端，否则不得将前端范围移到 `范围外`
- ❌ 不得用澄清问题 ID 作为唯一链接来源

**验收标准约束**:
- 必须是可观察和可测试的
- 必须附带源需求 ID
- 缺失边界、异常、字段、集成、权限验收标准时，必须在此处补充

**质量门禁**:
- ✅ 业务目标、范围、流程、规则、字段、依赖、非功能要求已体现
- ✅ 每个验收标准都有稳定引用和源需求 ID
- ✅ 没有前端范围被静默移到 `范围外`
- ✅ 没有 PRD 阻断性问题仍未解决

**设计意图**: 将结构化需求转换为人类可读的产品文档，作为下游用户故事生成的输入依据。

---

### 2.4 4p12s-user-stories（用户故事）

**职责**: 从 `requirements-register.md` 和 `prd.md` 生成用户故事和 Given/When/Then 验收场景。

**前置依赖**: `requirements-register.md`、`prd.md`

**输出产物**: `user-stories.md`

**核心结构**:
```markdown
## 场景总览（表格）
## 用户故事
### US-001 <故事标题>
#### AC-001 <验收场景标题>
- 场景用例 ID: SC-001
- 是否产品行为变更：是/否
- 最低验证层级：unit / component / service_api / service_integration / cross_boundary_e2e
- 是否提交前自动化验证：是/否
- 是否阻断 Git：是/否
```gherkin
Given ...
When ...
Then ...
```
```

**映射规则**（严格约束）:
- ✅ 范围内的每个需求 ID 必须出现在至少一个 `US-xxx` 中
- ✅ PRD 的每个验收标准必须映射到至少一个 `AC-xxx` / `SC-xxx`
- ✅ 范围内的前端或用户交互验收默认为 `cross_boundary_e2e`，必须标记为 Git 阻断
- ❌ 如果需要的验收场景没有对应的 PRD 验收标准，返回 `blocked` 而非凭空创建
- ❌ 不得引入上游产物中不存在的需求

**ID 所有权**:
- `US-xxx`、`AC-xxx`、`SC-xxx` 由 `user-stories.md` 拥有
- PRD 验收标准是输入依据，下游验收场景 ID 由本文件重新分配

**验证层级定义**:
| 层级 | 说明 |
|------|------|
| `unit` | 单元测试，隔离被测对象 |
| `component` | 组件测试，验证模块内部协作 |
| `service_api` | 服务 API 测试，验证 HTTP/RPC 接口 |
| `service_integration` | 服务集成测试，验证服务间调用 |
| `cross_boundary_e2e` | 跨边界 E2E，验证完整用户流 |

**设计意图**: 将产品需求转换为可测试的验收场景，为验证计划提供契约输入。

---

### 2.5 4p12s-technical-design（技术设计）

**职责**: 为已接受的业务范围生成技术设计文档，连接需求和验收场景到具体技术实现。

**前置依赖**: `requirements-register.md`、`prd.md`、`user-stories.md`

**输出产物**: `design.md`

**上下文发现策略**（渐进式披露）:
1. 首先读取项目入口文档（`.gientech/AGENTS.md`、`AGENTS.md` 或 README）
2. 仅跟进本次功能所需的文档
3. 当文档无法识别时，使用聚焦的符号或文本搜索
4. ❌ 禁止扫描整个仓库

**核心章节**:
1. 项目上下文
2. 实现范围（范围内/范围外）
3. 方案设计（模块与职责、接口/数据流/事件流、状态流、权限、配置、错误处理）
4. 设计元素清单
5. 需求到设计映射表
6. 测试与验证设计
7. 风险与开放问题

**设计元素清单**（强制要求）:
```markdown
| 设计元素 ID | 类型 | 名称 | 所属模块 | 来源需求 ID | 关联用户故事/验收场景 | 是否需要实现 | 是否需要验证 | 说明 |
```

**映射规则**:
- ✅ 范围内的每个需求 ID 必须有设计承接行或已记录的原因
- ✅ 每个 Git 阻断验收项必须有设计级验证策略
- ✅ 每个设计元素必须映射到上游需求 ID 和 `US-xxx` / `AC-xxx` / `SC-xxx`
- ✅ 每个范围内的前端交互都有前端设计范围和 E2E 验证策略
- ❌ 不得创建新的用户故事、验收场景或场景用例 ID
- ❌ 不得编造文件路径或 API

**设计意图**: 将业务需求翻译为技术方案，同时保持与上游需求的可追溯性。

---

### 2.6 4p12s-verification-plan（验证计划）

**职责**: 从上游交付产物生成验证计划，定义"要验证什么"，不回答"命令如何运行"。

**前置依赖**: `requirements-register.md`、`prd.md`、`user-stories.md`、`design.md`

**输出产物**: `verification-plan.md`

**验证契约边界**（强约束）:
- ✅ 必须生成：覆盖关系、验证层级、Git 阻断决策、目标测试文件、真实接口断言规则、禁用 Mock 规则
- ❌ 不写：启动或连接命令、端口和地址、健康检查命令、执行命令

**验证覆盖表**（核心资产）:
```markdown
| 来源需求 ID | 用户故事 ID | 验收场景 ID | 场景用例 ID | PRD 验收标准 | Given/When/Then 摘要 | 验证类型 | 验证对象层级 | 最低验证层级 | 是否允许降级验证 | 降级理由 | 是否产品行为变更 | 是否提交前自动化验证 | 是否阻断 Git | 是否自动化 | 目标测试文件/目录 | 所需真实服务类型 | 前端是否适用 | 测试数据要求 | 真实接口断言 | 禁用 Mock 规则 |
```

**覆盖规则**（严格约束）:
- ✅ 范围内的每个需求 ID 必须映射到至少一个测试用例或验证项
- ✅ PRD 的每个验收标准必须映射到至少一个测试用例
- ✅ `user-stories.md` 的每个 `AC-xxx` / `SC-xxx` 必须映射到至少一个测试用例
- ✅ `design.md` 的每个设计元素必须映射到至少一个测试用例或非代码处理决策
- ✅ 范围内的每个前端交互必须映射到至少一个前端 E2E 或 `cross_boundary_e2e` 验证用例
- ❌ 目标测试文件/目录不得使用占位符路径

**测试用例结构**:
```markdown
### TC-001 <用例标题>
- 关联需求 ID / 用户故事 ID / 验收场景 ID / 场景用例 ID
- 优先级：P0 / P1 / P2
- 类型：单元 / 接口 / 集成 / E2E 候选 / 人工验收 / 非代码验证 / 安全 / 性能
- 最低验证层级
- 是否提交前必须执行
- 未执行是否阻断 Git
- 目标测试文件/目录
- 所需真实服务类型
- 真实接口断言
- 禁用 Mock 规则
- 测试数据要求
- 步骤与预期结果
```

**设计意图**: 建立完整的验证契约，确保每个需求、设计元素都有对应的验证策略。

### 2.7 4p12s-implementation-tasks（开发任务计划）

**职责**: 把已确认的产品范围和技术设计转成 `tasks/` 下的开发计划，每个 Task 都是可独立 TDD 完成的小计划。

**前置依赖**: `requirements-register.md`、`prd.md`、`user-stories.md`、`design.md`

**输出产物**:
```
tasks/
├── index.md
├── TASK-001.md
└── TASK-xxx.md
```

**拆分原则**:
- ✅ 每个 Task 应对应一个可独立 TDD 完成的产品行为、服务能力、页面行为、接口能力或技术支撑变更
- ✅ 同一业务行为涉及 DTO、类型、路由、配置、页面、服务编排时，合并到直接使用它们的 Task
- ❌ 不生成独立 DTO、类型定义、路由、配置或纯文件改造 Task
- ❌ 不生成"后续补测试"Task
- ❌ 不生成 E2E 测试代码 Task
- ❌ Task ID 就是执行顺序，后面的 Task 可以依赖前面的，前面的不得依赖后面的

**TASK-xxx.md 结构**（TDD 四步骤）:
```markdown
## 目标
## 文件计划（Create / Modify / Test）
## TDD 步骤
- [ ] Step 1: 编写失败测试
- [ ] Step 2: 运行红灯验证
- [ ] Step 3: 实现最小代码
- [ ] Step 4: 运行绿灯验证
## 结果记录
```

**质量门禁**:
- ✅ 每个 Task 都包含失败测试、红灯验证、实现、绿灯验证四个基础步骤
- ✅ 每个 Task 都有明确文件计划
- ✅ 每个 Task 的红灯/绿灯命令来自项目规范或聚焦配置查找
- ❌ 没有 E2E 测试代码任务、集成测试执行任务、Git 任务或发布任务

**设计意图**: 将技术设计拆解为可执行的 TDD 任务单元，为自动化实现提供结构化指令。

---

### 2.8 4p12s-implementation-execution（开发任务执行）

**职责**: 执行选定的开发 Task，按 TDD 四步骤逐项完成。

**前置依赖**: `tasks/index.md`、`tasks/TASK-xxx.md`

**核心原则：自动连续执行**（关键心智模型）:
- ✅ Task 不是交付点：每个 Task 只是中间步骤，不要在每个 Task 完成后等待用户确认
- ✅ 默认连续执行：除非遇到 `failed` / `blocked`，否则必须自动继续执行下一个 Task
- ✅ 总结≠停止：可以在每个 Task 完成后简要记录，但记录后必须立即开始下一个 Task
- ✅ 只在阻塞时停止：TDD 绿灯验证真实失败、外部依赖缺失、需要用户决策

**反模式**（必须避免）:
- ❌ 每个 Task 完成后输出详细总结并等待用户确认
- ❌ 说"TASK-XXX 已完成，接下来需要执行 TASK-YYY，请确认"
- ❌ 把编译警告、lint 提示当作 `failed` 停下来
- ❌ 因为判断某个 Task"不适合 TDD"或"太简单"而跳过它

**执行顺序约束**（强制）:
- ✅ 必须严格按照 `tasks/index.md` 的 `Task 目录清单` 表格行序，从第一个未完成的 Task 开始逐个执行
- ❌ 禁止跳选、禁止重排
- ❌ 禁止以"该任务不适合 TDD""先做更有价值的任务"等理由跳过行序靠前的未完成 Task

**"未完成"的判定标准**:
- ✅ 已完成的定义：Task 文件中所有 Step checkbox 均为 `- [x]` **且** `## 结果记录` 中已有 `tdd_green_result` 证据
- ❌ 其余情况一律视为**未完成**：Task 文件缺失、checkbox 仍为 `- [ ]`、结果记录为空模板

**非 TDD 形态任务的处理**（脚手架、SQL、配置类）:
- ✅ 同样必须按行序执行，不得跳过
- ✅ 红灯步骤：以任务文件计划中产物的"缺失"作为红灯证据
- ✅ 绿灯步骤：执行该 Task 文件中给出的验证命令（build、lint、prisma generate、SQL 执行等）
- ❌ 若 Task 文件没有给出任何可执行的验证命令且无法推导出验证方式，返回 `blocked`，**禁止跳过**

**TDD 四步骤**（强制要求）:
1. **Step 1 编写失败测试**: 目标测试文件、测试意图、关键断言
2. **Step 2 运行红灯验证**: cwd、command、期望结果（失败）、证据
3. **Step 3 实现最小产品代码**: 变更文件、实现说明
4. **Step 4 运行绿灯验证**: cwd、command、期望结果（通过）、证据

**结果记录**（结构化证据）:
```yaml
changed_files: [...]
tests_added_or_changed: [...]
commands_run:
  - cwd: ...
    command: ...
    exit_code: ...
    result: ...
    output_summary: ...
tdd_red_result: ...
tdd_green_result: ...
requirement_ids_covered: [...]
user_stories_covered: [...]
```

**返回状态**:
- `passed`: 当前 Task 所有 TDD 步骤完成且绿灯验证通过 → **继续执行下一个 Task**
- `failed`: 绿灯验证真实失败 → **停止执行**
- `blocked`: 遇到外部依赖缺失或环境问题 → **停止执行**

**设计意图**: 实现真正的测试驱动开发自动化，确保每个 Task 都有可验证的交付证据。

### 2.9 4p12s-integration-test（集成测试）

**职责**: 运行真实 API 和服务间集成验证，在内部完成运行、归因、修复、重跑的完整循环。

**前置依赖**: `verification-plan.md`、`verification-result.md`

**输出产物**: 追加写入 `verification-result.md` 的集成部分

**执行流程**（三步强规则）:
1. **STEP-01: 服务启动**
   - 从 `verification-plan.md` 提取所需真实服务类型、测试数据要求、禁用 Mock 规则
   - 从项目入口文档发现后端/API 启动命令、地址/端口、健康检查方式
   - 实际执行启动命令，在后台启动后端服务
   - 执行健康检查
   - ❌ 缺少任一证据都不得返回 `passed`

2. **STEP-02: 测试数据准备**
   - 按 `verification-plan.md` 中的测试数据要求准备初始数据
   - 记录数据准备的最小执行证据

3. **STEP-03: 运行集成测试**
   - 执行从项目入口文档发现的集成测试命令
   - 逐项执行每个集成测试 TC
   - 记录每个 TC 的最小执行证据

**修复循环**:
1. 对每个失败 TC，归因失败原因（产品代码、测试代码、环境、数据、配置）
2. 渐进式披露：修复代码时，按失败 TC → `user-stories.md` → `prd.md` 的路径，只读取关联条目
3. 修复对应的产品代码或测试代码
4. 重跑失败 TC + 受影响的回归项
5. 重复直到全部通过或达到 5 轮上限
6. 超过 5 轮后返回 `blocked` 或 `failed`

**强规则**（必须遵守）:
- ✅ **没有服务启动证据不得返回 `passed`**
- ✅ **没有健康检查结果不得返回 `passed`**
- ✅ **"测试代码已创建"、"文件存在"、"CI 稍后运行"、纯编译通过不是集成测试通过证据**
- ✅ **每个集成测试 TC 必须有真实执行记录**
- ✅ **只有 STEP-01 到 STEP-03 都满足完成条件并有证据，才允许返回 `passed`**

**最小执行证据规则**:
- ✅ 只记录发现来源、执行动作、命令摘要、结果、关键输出摘要
- ✅ 命令摘要格式：`<cwd> <command>`
- ❌ 不记录完整 stdout/stderr
- ❌ 不能只写"完成""已执行""通过"

**设计意图**: 验证服务间真实集成，确保 API 调用、数据持久化、状态变更等跨模块行为正确。

### 2.10 4p12s-e2e-test（端到端测试）

**职责**: 完整的 E2E 阶段：写测试代码 → 启动真实服务 → 准备数据 → 执行真实 E2E → 修复失败 → 重跑直到通过。

**前置依赖**: `verification-plan.md`、`verification-result.md`

**输出产物**: 追加写入 `verification-result.md` 的 E2E 部分

**关键约束**（与开发任务阶段的区别）:
- ✅ 开发任务阶段**不写**E2E 测试代码
- ✅ 本阶段**必须**根据 `verification-plan.md` 中的测试用例契约补齐 E2E 测试代码

**E2E 测试代码编写要求**:
- ✅ 使用 `verification-plan.md` 指定的目标测试文件
- ✅ 覆盖每个 E2E / `cross_boundary_e2e` TC
- ✅ 前端用户流测试必须通过真实前端和真实后端/API 交互
- ✅ 测试必须包含真实接口断言，不能只断言静态页面、loading、路由跳转或 mock 响应
- ❌ 禁止在 E2E 测试代码中使用 `page.route().fulfill()`、`intercept`、`mock`、`jest.fn()` 或任何请求拦截/伪造响应的手段
- ❌ 不得凭空发明新的业务范围

**服务启动和真实验证**（强制要求）:
- ✅ 前端用户流：必须启动或连接前端服务和后端/API 服务
- ✅ API E2E / 跨服务 E2E：必须启动或连接目标 API/服务和必要依赖服务
- ✅ 记录最小执行证据
- ✅ 执行每个必需服务的健康检查
- ❌ 健康检查不通过不得继续执行 E2E

**修复循环**:
1. 对失败 TC 归因：产品代码、E2E 测试代码、环境、测试数据、配置
2. 按失败 TC 关联的 US/AC/SC 和 PRD 读取必要上下文
3. 修复前端代码、后端代码、配置、测试数据或 E2E 测试代码
4. 重跑失败 TC 和受影响回归项
5. 最多 5 轮。超过后返回 `blocked` 或 `failed`

**通过条件**（全部满足才返回 `passed`）:
- ✅ 每个 E2E TC 都有目标测试代码
- ✅ 当前 E2E 用例所需的所有真实服务都已启动或连接，并有健康检查证据
- ✅ 前端用户流包含真实前端和真实后端/API 证据
- ✅ 测试数据已准备或明确无需准备
- ✅ E2E 命令已真实执行
- ✅ 所有提交前必须执行的 E2E TC 都通过
- ✅ 每个 E2E TC 都有真实接口断言证据
- ❌ 只写了测试代码但没有运行 → 不得返回 `passed`
- ❌ 只运行了前端 webServer 或静态页面检查 → 不得返回 `passed`
- ❌ 没有真实服务或真实 API 证据 → 不得返回 `passed`
- ❌ 使用 mock 结果作为通过证据 → 不得返回 `passed`

**设计意图**: 验证完整用户流和跨系统边界的行为，确保最终交付物符合业务需求。

### 2.11 4p12s-git-push（Git 推送）

**职责**: 执行交付流程的 Git 提交和推送步骤，验证通过后仅暂存交付相关文件、提交、推送、验证远端 HEAD。

**前置依赖**: `verification-result.md`（必须包含 `## E2E 验证结果` 且结论为通过）

**前置检查**（强约束）:
- ❌ `verification-result.md` 缺失、为空、没有 `## E2E 验证结果`、E2E 验证结论不是通过、列出了 Git 阻断项 → 返回 `blocked`
- ❌ `delivery-state.md` 中的 `verification_e2e` Step 不是 `passed`（编排模式下）→ 返回 `blocked`

**提交信息规范**（commit-msg 格式，核心约束）:
```
${commit}:${taskId}_${name}：${submitDescription}
```

> ⚠️ **关键细节**: `name` 与 `submitDescription` 之间的冒号是**中文全角冒号 `：`**，其余均为英文半角。

| 字段 | 说明 | 取值约束 |
|------|------|----------|
| `commit` | 提交类型 | `Feat`（需求）/ `Task`（任务）/ `BugFix`（缺陷） |
| `taskId` | 任务/需求 ID，不可含下划线 `_` | 如 `33413` |
| `name` | 任务/需求名称，**可含中文冒号 `：`**，贪婪匹配到最后一个 `：` 为分隔符 | 如 `新增 harness 的使用`、`需求：新增 harness` |
| `submitDescription` | 本次提交描述，不可为空 | 如 `add harness L1 integration` |

**示例**:
```
Feat:33413_新增 harness 的使用：add harness L1 integration
Task:33414_代码审查优化：optimize review logic
BugFix:33415_修复空指针：resolve null pointer exception
```

**❌ 错误示例**（name 中被插入了全角空格，肉眼难以发现）:
```
Task:33413_新增 harness 的使用：refactor wiki structure
```
原始 title 是 `新增 harness 的使用`，中间没有空格。插入的全角空格在终端里看起来像普通空格，但 husky hook 会校验失败。

**✅ 正确示例**:
```
Task:33413_新增 harness 的使用：refactor wiki structure
```

**任务信息提取流程**（提交前必须执行）:
1. **搜索上下文中的任务信息**:
   - 当前会话上下文（系统提示词注入的 XML）：`<work_task_context source="selected_work_task">`
   - 编排模式的 `tasks/index.md`：已通过的 Task 记录
   - `delivery-state.md` 中的任务关联字段

2. **提取字段映射**:
   | 提取字段 | 映射到 commit-msg |
   |----------|-------------------|
   | `<task_type>` | `commit`（`DEFECT`→`BugFix`；`BUSINESS_REQUIREMENT`→`Feat`；`TECHNICAL_REQUIREMENT`→`Task`） |
   | `<task_id>` | `taskId` |
   | `<title>`（仅去掉 `【...】` 前缀标签） | `name` |
   | `git diff --stat` + 暂存文件的变更摘要 | `submitDescription` |

3. **任务信息缺失时的处理**:
   - 提示用户填写任务信息
   - 用户选择"强制跳过"时使用默认值：`Task:0000_untitled：update files per git diff stat`

**范围选择**（文件暂存规则）:
- ✅ 从交付产物、当前交付目录、已通过 Task 记录、`verification-result.md`、`git status` 确定本次交付的文件集
- ✅ 仅暂存属于本次交付的明确路径，保留无关变更
- ❌ 如果交付文件集无法与无关变更分离，返回 `blocked`

**执行流程**:
1. 运行 `git status` 和聚焦的 `git diff`
2. 确定本次交付的明确文件列表
3. 仅暂存这些明确路径
4. **【必须】提取任务信息**
5. 按 commit-msg 格式模板直接填充组装
6. 执行 `git commit -m "<组装好的 commit-msg>"`
7. 推送当前分支
8. 验证远端分支 HEAD 等于本地提交哈希
9. 向 `deploy-log.md` 追加一条新的 Git Push 记录

**deploy-log.md##Git Push 写入规则**（追加，不覆盖）:
- ❌ 不存在：创建文件，写入标题和章节，再追加本次记录
- ❌ 存在但没有 `## Git Push` 章节：在文件末尾追加该章节，再追加本次记录
- ✅ 已有 `## Git Push` 章节：完整读取文件现有内容，把本次记录追加到该章节末尾
- ❌ 每次执行本 Skill 只追加一条新记录；**严禁删除、覆盖或重排历史 Git Push 记录**
- ✅ 记录编号自增：`record_no` = 现有 Git Push 记录条数 + 1，首条为 1

**记录模板**:
```markdown
### Git Push #<record_no>

- record_no:
- push_time:              # ISO8601 时间戳
- commit_type:            # Feat | Task | BugFix
- task_id:
- task_name:
- commit_hash:
- branch:
- remote:
- staged_files:
- commit_message:         # 完整 commit-msg，含中文冒号
- commit_command:
- commit_exit_code:
- push_command:
- push_exit_code:
- remote_head_check_command:
- remote_head:
- result:
```

**边界**（禁止事项）:
- ❌ 不触发发布或部署 API
- ❌ 不写入 `deploy-log.md##Release Trigger`
- ❌ 不覆盖、删除或改写 `deploy-log.md` 中的历史记录与其他章节，仅追加本次记录
- ❌ 不创建或切换分支
- ❌ 不创建、打开、准备或等待 Pull Request / Merge Request

**设计意图**: 确保 Git 提交信息符合项目规范，建立可追溯的交付历史记录。

### 2.12 4p12s-deployment-execution（发布触发）

**职责**: 在 Git 推送成功后触发发布 API 或发布脚本，并将返回状态写入 `deploy-log.md##Release Trigger`。

**前置依赖**: `deploy-log.md` 中的 `## Git Push` 章节（存在多条记录时以最新一条为准）

**输出产物**: 追加写入 `deploy-log.md` 的 Release Trigger 部分

**发布入口发现**（优先级顺序）:
1. 项目根目录 `scripts/deploy.sh`
2. 项目入口文档指定的发布脚本、命令、CI/CD 平台或发布说明
3. `package.json`、Makefile、CI 配置或仓库脚本中明确命名的发布命令
4. 用户在当前交付中显式指定的发布方式
5. ❌ 如果无法确定发布入口、发布环境、目标分支或凭证来源，返回 `blocked`，不得猜测

**凭证规则**（安全约束）:
- ❌ 不得在 Skill 指令、交付文档或代码中写入 CI/CD webhook URL、api-token、账号密码或长期凭证
- ✅ 发布凭证只能来自项目认可的位置（环境变量、凭证管理器、CI/CD 平台配置、项目入口文档）
- ❌ 如果发布命令需要凭证但当前环境不可用，返回 `blocked`

**执行流程**:
1. 读取 `delivery-state.md`、`deploy-log.md`、项目入口文档和发布说明
2. 从最新一条 Git Push 记录中提取提交哈希、目标分支和远端信息
3. 发现发布入口，优先使用 `scripts/deploy.sh`
4. 执行发布命令或调用发布 API
5. 记录命令、环境、提交哈希、目标分支、HTTP/进程状态和响应摘要
6. 向 `deploy-log.md##Release Trigger` 追加本次记录
7. 返回 `STEP_RESULT`

**deploy-log.md##Release Trigger 写入规则**（追加，不覆盖）:
- ❌ 没有 `## Release Trigger` 章节：在文件末尾追加该章节，再追加本次记录
- ✅ 已有 `## Release Trigger` 章节：完整读取文件现有内容，把本次记录追加到该章节末尾
- ❌ 每次执行本 Skill 只追加一条新记录；**严禁删除、覆盖或重排历史 Release Trigger 记录**
- ✅ 记录编号自增：`record_no` = 现有 Release Trigger 记录条数 + 1，首条为 1

**记录模板**:
```markdown
### Release Trigger #<record_no>

- record_no:
- trigger_time:
- commit_hash:
- target_branch:
- environment:
- deploy_entry:
- deploy_command:
- exit_code:
- credential_source:
- response_summary:
- result:
```

**结论枚举**（固定值，不得发明新状态）:
- `请求已受理`
- `请求失败`
- `凭证缺失`
- `入口缺失`
- `结果无法判断`

**边界**（禁止事项）:
- ❌ 不决定 workflow terminal state
- ❌ 不改写 `deploy-log.md##Git Push`
- ❌ 不覆盖、删除或改写 `deploy-log.md` 中的历史记录，仅追加本次记录
- ❌ 不创建、打开、准备或等待 Pull Request / Merge Request
- ❌ Pull Request / Merge Request 创建、MR ready、等待合并都不是发布触发

**设计意图**: 触发最终的发布流程，将交付物部署到目标环境。

## 四、核心设计模式

### 4.1 状态账本模式

**定义**: 通过 `delivery-state.md` 统一跟踪交付进度、阻塞原因和证据文件。

**优势**:
- 单一事实来源：所有阶段的状态都记录在同一个文件中
- 可追溯性：每个阶段的产物都有明确的证据文件路径
- 可恢复性：中断后可以从 `current_step` 继续执行
- 可审计性：每个阶段的执行结果都有结构化证据

**状态流转规则**:
```
pending → running → passed → (下一阶段的 pending)
                ↓
            blocked / failed → 等待用户干预
```

### 4.2 双模运行模式

**定义**: 每个技能支持编排模式（被 orchestrator 调用）和独立模式（用户直接调用）。

**编排模式**:
- 接收路径包参数
- 不直接更新 `delivery-state.md`（由 orchestrator 统一处理）
- 返回 `STEP_RESULT` 结构化结果

**独立模式**:
- 自动发现项目根目录、入口文档、上游产物
- 直接更新 `delivery-state.md`
- 直接面向用户输出产物文件

**优势**:
- 灵活性：既可以自动化编排，也可以手动执行单个阶段
- 可测试性：每个技能可以独立测试
- 可组合性：可以根据需要组合不同的技能

### 4.3 稳定 ID 追溯模式

**定义**: 从需求到代码的每个工件都有稳定的 ID，形成完整的追溯链。

**ID 类型**:
- 源需求 ID：`BR-xxx`、`FUNC-xxx`、`UI-xxx`、`NFR-xxx` 等
- 用户故事 ID：`US-xxx`
- 验收场景 ID：`AC-xxx`
- 场景用例 ID：`SC-xxx`
- 测试用例 ID：`TC-xxx`
- 设计元素 ID：`DE-xxx`
- 开发任务 ID：`TASK-xxx`

**追溯链**:
```
源需求 ID → PRD 验收标准 → US-xxx → AC-xxx → SC-xxx → TC-xxx → TASK-xxx → 代码文件
```

**优势**:
- 变更影响分析：修改某个需求时，可以快速定位受影响的代码
- 覆盖验证：确保每个需求都有对应的测试和实现
- 文档一致性：避免文档与代码脱节

### 4.4 TDD 自动化模式

**定义**: 在 implementation-execution 阶段强制执行"红灯→实现→绿灯"的测试驱动开发流程。

**四步骤**:
1. **编写失败测试**: 定义期望行为，测试失败
2. **运行红灯验证**: 确认失败原因指向目标能力缺失
3. **实现最小代码**: 只实现让测试通过的最小代码
4. **运行绿灯验证**: 确认测试通过

**约束**:
- ❌ 不得跳过红灯步骤
- ❌ 编译、lint、类型检查不能作为红灯验证
- ✅ 每个步骤都必须有结构化证据
- ✅ 只有绿灯验证通过后才能标记 Task 为 `passed`

**优势**:
- 保证测试覆盖率
- 避免过度设计
- 提供可验证的交付证据

### 4.5 真实验证模式

**定义**: 在 integration-test 和 e2e-test 阶段必须使用真实服务和真实接口断言。

**约束**:
- ✅ 必须启动或连接真实服务（前端、后端、数据库等）
- ✅ 必须执行健康检查
- ✅ 必须准备真实测试数据
- ✅ 必须包含真实接口断言
- ❌ 禁止使用 mock 结果作为通过证据
- ❌ 禁止在 E2E 测试代码中使用 `page.route().fulfill()`、`intercept`、`mock` 等手段

**优势**:
- 发现真实环境问题
- 验证服务间集成
- 避免"测试通过但生产失败"的情况

### 4.6 最小执行证据模式

**定义**: 每个步骤的执行结果必须记录结构化证据，而非简单的"通过/失败"。

**证据格式**:
```yaml
commands_run:
  - cwd: /path/to/dir
    command: npm test
    exit_code: 0
    result: passed
    output_summary: 15 tests passed
```

**约束**:
- ✅ 命令摘要格式：`<cwd> <command>`
- ✅ 记录发现来源、执行动作、结果、关键输出摘要
- ❌ 不记录完整 stdout/stderr
- ❌ 不能只写"完成"、"已执行"、"通过"

**优势**:
- 可复现性：其他人可以按证据复现执行过程
- 可调试性：失败时可以快速定位问题
- 可审计性：提供可信的执行记录

## 五、质量门禁体系

### 5.1 各阶段质量门禁

| 阶段 | 质量门禁 |
|------|----------|
| requirements | 每个前端信号映射到 `UI-*`；没有下游专属内容；澄清 ID 不替代源需求 ID |
| prd | 业务目标/范围/流程/规则已体现；每个验收标准都有源需求 ID；没有前端范围被静默移到范围外 |
| user-stories | 每个需求 ID 映射到 US；每个 PRD 验收标准映射到 AC/SC；每个 AC 都有完整 Given/When/Then |
| technical-design | 每个需求 ID 都有设计承接；每个 Git 阻断项都有验证策略；每个设计元素都映射到上游需求 |
| verification-plan | 每个需求/设计元素都映射到 TC；每个 TC 都有目标测试文件；每个前端交互都有 E2E 用例 |
| implementation-tasks | 每个 Task 都有 TDD 四步骤；没有 E2E 测试代码任务 |
| implementation-execution | 每个 Task 的 TDD 步骤都有证据；红灯/绿灯验证都真实执行 |
| integration-test | 服务启动证据完整；健康检查通过；每个 TC 都有真实执行记录 |
| e2e-test | 真实服务启动；真实接口断言；没有使用 mock；所有提交前 TC 都通过 |
| git-push | commit-msg 格式正确；远端 HEAD 一致性验证通过；deploy-log 记录完整 |
| deployment-execution | 发布入口明确；凭证来源合法；发布命令执行成功 |

### 5.2 跨阶段一致性检查

- ✅ 需求 ID 覆盖：范围内的每个需求 ID 在所有下游产物中都有对应行
- ✅ 前端交互覆盖：每个 `UI-*` 需求在 PRD、US、design、verification-plan、E2E 测试中都有对应内容
- ✅ Git 阻断项追踪：user-stories 中标记为 Git 阻断的验收项，在 verification-plan 中必须有验证路径，在 e2e-test 中必须有通过证据
- ✅ 产物文件路径一致性：verification-plan 中指定的目标测试文件必须与项目运行器配置一致

## 六、禁止事项汇总

### 6.1 各阶段禁止事项

| 阶段 | 禁止事项 |
|------|----------|
| delivery-orchestrator | 调用子技能；执行任何 Step；修改 delivery-state.md 之外的文件 |
| requirements | 创建 prd.md、user-stories.md 等下游产物；删除原始需求文本；将前端信号降级为仅 NFR-* |
| prd | 转为技术设计；创建 user-stories.md、design.md 等；将前端范围静默移到范围外 |
| user-stories | 创建技术设计、验证计划、任务、代码、提交或部署产物；引入上游不存在的需求 |
| technical-design | 创建 verification-plan.md、tasks/、代码、提交或部署产物；编造文件路径或 API |
| verification-plan | 编写自动化测试代码；运行测试；编辑产品代码；创建 tasks/ |
| implementation-tasks | 实现代码；执行测试；做 Git 或发布；生成 E2E 测试代码任务 |
| implementation-execution | 改写 tasks/index.md；写 E2E 测试代码；运行最终集成测试和 E2E 测试；提交、推送、发布 |
| integration-test | 运行 E2E 测试；提交、推送、发布；没有服务启动证据就返回 passed |
| e2e-test | 重复运行集成测试（除非 E2E 修复影响了集成边界）；提交、推送、发布；使用 mock 结果作为通过证据 |
| git-push | 触发发布或部署 API；写入 deploy-log.md##Release Trigger；创建或切换分支；创建/等待 PR/MR |
| deployment-execution | 决定 workflow terminal state；改写 deploy-log.md##Git Push；创建/等待 PR/MR |

### 6.2 通用禁止事项

- ❌ 不得在文档、代码或指令中写入敏感凭证（api-token、webhook URL、账号密码）
- ❌ 不得使用占位符路径作为目标测试文件
- ❌ 不得将编译警告、lint 提示当作 TDD 红灯验证
- ❌ 不得跳过行序靠前的未完成 Task 去执行后面的 Task
- ❌ 不得在每个 Task 完成后等待用户确认（除非遇到 failed/blocked）
- ❌ 不得将 MR/PR 创建、MR/PR ready、等待合并当作发布触发
- ❌ 不得覆盖、删除或改写 deploy-log.md 中的历史记录

## 七、适用场景与限制

### 7.1 适用场景

✅ **适合使用 4P12S 的场景**:
- 新功能开发（从需求到发布的完整交付）
- 缺陷修复（从缺陷描述到修复验证）
- 技术重构（从技术方案到验证）
- 需要完整追溯链的合规项目
- 需要自动化 TDD 的项目
- 需要真实集成验证的微服务项目

### 7.2 不适用场景

❌ **不适合使用 4P12S 的场景**:
- 简单的文档更新（无需 TDD 和集成测试）
- 紧急热修复（流程过于冗长）
- 探索性原型开发（需求不明确，需要快速迭代）
- 纯配置变更（无需代码实现和测试）
- 已有成熟 CI/CD 流程且不需要变更的项目

### 7.3 限制与约束

- **流程冗长**: 完整执行 12 个技能需要较长时间，不适合快速交付场景
- **文档负担**: 需要生成和维护大量文档（requirements-register.md、prd.md、user-stories.md、design.md、verification-plan.md、tasks/、verification-result.md、deploy-log.md）
- **技能依赖**: 需要项目具备完善的入口文档、测试框架、发布脚本等基础设施
- **环境要求**: integration-test 和 e2e-test 阶段需要真实的服务环境
- **凭证管理**: 发布触发阶段需要合法的凭证来源

## 八、最佳实践建议

### 8.1 文档维护

- ✅ 使用版本控制管理所有交付文档
- ✅ 在 `delivery-state.md` 中准确记录每个阶段的证据文件路径
- ✅ 定期审查 `deploy-log.md` 中的历史记录，确保追溯链完整
- ✅ 使用统一的 ID 命名规则，避免 ID 冲突

### 8.2 技能编排

- ✅ 使用 `4p12s-delivery-orchestrator` 初始化交付状态
- ✅ 按依赖顺序依次触发技能，不要跳过前置阶段
- ✅ 在 `blocked` 或 `failed` 时及时干预，避免无效执行
- ✅ 对于简单变更，可以只执行相关技能（如只执行 requirements + prd）

### 8.3 TDD 执行

- ✅ 严格按照 `tasks/index.md` 的行序执行 Task
- ✅ 不要跳过红灯步骤，即使任务看起来很简单
- ✅ 为每个 Task 记录完整的结构化证据
- ✅ 对于非 TDD 形态任务（脚手架、SQL、配置），也要定义明确的红灯/绿灯验证命令

### 8.4 真实验证

- ✅ 在 `verification-plan.md` 中明确声明所需真实服务类型
- ✅ 在 `integration-test` 和 `e2e-test` 阶段执行健康检查
- ✅ 准备可复用的测试数据准备脚本
- ✅ 禁止在 E2E 测试代码中使用任何 mock 手段

### 8.5 Git 提交

- ✅ 严格按照 commit-msg 格式模板组装提交信息
- ✅ 注意中文全角冒号 `：` 的使用
- ✅ 不要在 name 字段中插入全角空格或零宽字符
- ✅ 从 `git diff` 总结 submitDescription，不要照搬任务描述

### 8.6 发布触发

- ✅ 优先使用 `scripts/deploy.sh` 作为发布入口
- ✅ 从环境变量或凭证管理器获取发布凭证
- ✅ 记录发布命令的执行结果和响应摘要
- ✅ 不要将 MR/PR 创建当作发布触发

## 九、总结

### 9.1 技能体系价值

4P12S 端到端交付技能体系提供了一套**标准化、可追溯、可验证**的软件交付流程，核心价值包括：

1. **需求追溯**: 从源需求到代码的完整追溯链，确保每个需求都有对应的实现和验证
2. **TDD 自动化**: 强制执行测试驱动开发，保证测试覆盖率和代码质量
3. **真实验证**: 使用真实服务和真实接口断言，避免"测试通过但生产失败"
4. **状态账本**: 通过 `delivery-state.md` 统一跟踪交付进度，支持中断恢复
5. **双模运行**: 支持自动化编排和手动执行，适应不同场景
6. **证据链**: 每个步骤都有结构化证据，提供可信的执行记录

### 9.2 适用团队

- ✅ 需要合规追溯的企业级项目
- ✅ 追求高质量和可维护性的团队
- ✅ 微服务架构，需要真实集成验证
- ✅ 已有成熟基础设施（入口文档、测试框架、发布脚本）的团队

### 9.3 未来改进方向

- **流程优化**: 对于简单变更，可以提供简化流程（跳过部分阶段）
- **工具支持**: 提供可视化的交付状态跟踪工具
- **技能扩展**: 支持更多类型的交付场景（如数据迁移、配置变更）
- **性能优化**: 优化技能执行时间，减少不必要的文件读取和命令执行
