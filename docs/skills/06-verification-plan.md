## 分析说明

### 1. 设计意图

**4p12s-verification-plan** 是 4P12S 技能体系的**验证契约定义器**，负责定义"要验证什么"，而不回答"命令如何运行"。它的核心价值在于：

- **验证覆盖**: 确保每个需求、用户故事、验收场景和设计元素都有对应的验证
- **验证分层**: 为每个验证项指定合适的验证层级
- **真实验证**: 定义真实接口断言和禁用 Mock 规则
- **测试数据**: 定义测试数据要求

这种设计的优势：
1. **验证完整**: 没有遗漏的验证项
2. **验证分层**: 不同验证项使用不同层级，避免过度测试
3. **真实验证**: 使用真实服务和真实接口断言
4. **可执行性**: 为下游执行阶段提供明确的验证契约

### 2. 核心概念解析

#### 2.1 验证契约边界

**核心原则**: 本阶段只回答"要验证什么"，不回答"命令如何运行"。

**必须生成**:
- ✅ 覆盖关系：需求、用户故事、验收场景和设计元素
- ✅ 验证层级：unit / component / service_api / service_integration / cross_boundary_e2e
- ✅ Git 阻断与提交前自动化决策
- ✅ 目标测试文件或测试目录约定
- ✅ 真实接口断言、禁用 Mock 规则和测试数据要求
- ✅ 执行期所需真实服务类型
- ✅ 前端是否适用

**不写**:
- ❌ 启动或连接命令、端口和地址
- ❌ 健康检查命令、集成测试命令、E2E 命令
- ❌ 命令来源证据

**示例**:
- ✅ "验证用户注册接口，使用真实数据库，禁用 Mock"
- ❌ "运行命令：docker-compose up -d mysql"

### 3. 覆盖规则

**核心规则**:

1. **需求覆盖**: 范围内的每个需求 ID 必须映射到至少一个测试用例或验证项
2. **PRD 验收标准覆盖**: PRD 的每个验收标准必须映射到至少一个测试用例
3. **用户故事覆盖**: user-stories.md 的每个 AC-xxx / SC-xxx 必须映射到至少一个测试用例
4. **设计元素覆盖**: design.md 的设计元素清单中的每个元素必须映射到至少一个测试用例或非代码处理决策
5. **验证层级匹配**: 公共入口点、API、路由、控制器、集成调用、持久化状态变更、前端页面的最低验证层级必须匹配外部可观察边界
6. **Git 阻断覆盖**: Git 阻断验收项必须有提交前验证路径或列为阻断项
7. **目标测试文件**: 目标测试文件/目录必须是完整的项目相对路径，不要使用占位符
8. **前端交互覆盖**: 每个范围内的前端交互必须映射到至少一个前端 E2E 或 cross_boundary_e2e 验证用例
9. **前端 E2E 要求**: 前端 E2E 用例必须设置提交前自动化验证，并声明 frontend 和后端真实服务类型
10. **前端 E2E 断言**: 前端 E2E 用例不能只依赖静态渲染、loading、路由导航或纯 UI 断言

### 4. 质量门禁

返回前必须验证的 9 项要求：

| 验证项 | 说明 | 检查方法 |
|--------|------|----------|
| 文件结构完整 | 包含所有必需章节 | 检查 Markdown 结构 |
| 测试用例 ID 稳定 | 每个测试用例都有稳定的 `TC-xxx` ID | 检查测试用例 |
| 引用存在于上游 | 测试用例引用的 US-xxx、AC-xxx、SC-xxx 都存在于上游 | 检查 user-stories.md |
| 需求 ID 覆盖 | 所有需求 ID 都已覆盖 | 检查需求登记表 |
| PRD 验收标准覆盖 | 所有 PRD 验收标准都已覆盖 | 检查 PRD |
| 设计元素覆盖 | 所有设计元素都已覆盖 | 检查 design.md |
| Git 阻断项有验证路径 | 每个 Git 阻断项都有验证路径或列为阻断项 | 检查验证覆盖表 |
| 提交前用例有完整声明 | 每个提交前用例都有目标测试文件/目录、真实服务类型、测试数据要求、真实接口断言和禁用 Mock 规则 | 检查验证覆盖表 |
| 前端交互有 E2E 用例 | 每个范围内的前端交互都有 E2E 用例 | 检查验证覆盖表 |

### 8. 常见问题

#### Q1: 验证计划可以包含命令吗？

**答**: 不可以。验证计划只回答"要验证什么"，不回答"命令如何运行"。命令是 execution 阶段的职责。

#### Q2: 如何确定验证层级？

**答**: 根据验证对象和边界确定：
- 前端交互 → cross_boundary_e2e
- API 接口 → service_api
- 服务集成 → service_integration
- 单一逻辑 → unit

#### Q3: 如何处理无法自动化的验证项？

**答**: 标记为"是否自动化=否"，并说明原因：
- 性能测试（需要专业工具）
- 安全测试（需要人工审计）
- 兼容性测试（需要多环境）

### 9. 适用场景

✅ **适合使用 verification-plan 的场景**:
- 已有 PRD、用户故事和技术设计
- 需要验证计划
- 需要验证覆盖

❌ **不适合使用 verification-plan 的场景**:
- 没有上游产物
- 简单的文档更新（无需验证计划）
- 紧急热修复（流程过于冗长）

**4p12s-verification-plan** 是 4P12S 技能体系的验证契约定义器，负责定义"要验证什么"。它通过验证覆盖表、验证层级指定和真实验证规则，确保验证完整、分层、真实。
