- **技能名称**: 4p12s-prd

- **版本**: v1.0.3

## 原文核心内容

### 概述

从已登记的业务需求生成 `prd.md`。保留业务含义，不转为技术设计。

### 双模运行

#### 编排模式

路径包必须包含：

```yaml
delivery_dir:
state_path:
project_entry_path:
requirements_register_path:
prd_path:               # 已存在的 prd.md 路径（更新场景）
output_paths:
allowed_write_paths:    # 仅 prd.md
```

#### 独立模式

自动发现：
- 当前目录或指定目录下的 `requirements-register.md`
- 项目入口文档
- 输出路径：与 `requirements-register.md` 同目录的 `prd.md`

如果找不到 `requirements-register.md`，提示用户先运行 `/4p12s-requirements`。

### PRD 规则

- 范围内的每个需求 ID 必须出现在 PRD 中，或在 `范围外` 中附带原因
- 保留 `requirements-register.md` 中的业务含义；不要将其转为技术设计
- 验收标准必须是可观察和可测试的
- 每个范围内的 `UI-*` 需求必须出现在用户角色/场景、功能范围、流程和验收标准中
- 除非 `requirements-register.md` 明确排除前端，否则不要将前端范围移到 `范围外`
- PRD 验收标准是下游验收场景生成的输入依据
- 如果 PRD 生成时发现缺失边界、异常、字段、集成、权限或非功能验收标准，在此处添加并附带源需求 ID
- 保持未解决的非阻断性问题明确
- 不要在没有标记来源的情况下引入新需求
- 不要使用澄清问题 ID 作为唯一链接来源

### 质量门禁

返回前验证：

- 源需求 ID 已覆盖
- 业务目标、范围、流程、规则、字段、依赖和非功能要求在存在上游内容时已体现
- 验收标准足够具体，可以供给验收场景生成
- 每个验收标准都有稳定引用和源需求 ID
- 每个范围内的 `UI-*` 需求都有 PRD 覆盖和至少一个可观察的验收标准
- 没有前端范围被静默移到 `范围外`
- 没有 PRD 阻断性问题仍未解决
- 没有编造不受支持的需求

## 分析说明

### 1. 设计意图

**4p12s-prd** 是 4P12S 技能体系的**产品文档生成器**，负责将结构化的源需求转换为人类可读的产品需求文档（PRD）。它的核心价值在于：

- **业务翻译**: 将结构化的需求条目翻译为连贯的产品文档
- **范围界定**: 明确功能范围内和范围外的内容
- **流程定义**: 描述主流程、异常流程和边界流程
- **验收标准**: 定义可观察和可测试的验收标准

这种设计的优势：
1. **业务可读**: PRD 是业务人员和技术人员都能理解的文档
2. **范围清晰**: 明确范围内和范围外，避免范围蔓延
3. **可测试性**: 验收标准可供给下游生成验收场景
4. **需求追溯**: 每个 PRD 条目都可以追溯到源需求 ID

### 2. 核心概念解析

#### 2.1 PRD 结构（10 个章节）

PRD 包含 10 个固定章节：

| 章节 | 内容 | 作用 |
|------|------|------|
| 1. 背景与目标 | 业务背景、目标、成功标准 | 说明"为什么做" |
| 2. 用户角色与场景 | 角色、场景、目标 | 说明"谁在什么情况下使用" |
| 3. 功能范围 | 范围内/范围外 | 说明"做什么"和"不做什么" |
| 4. 业务流程 | 主流程、异常流程、边界流程 | 说明"业务如何流转" |
| 5. 业务规则 | 业务规则列表 | 说明"业务约束条件" |
| 6. 字段、数据与状态口径 | 字段定义、数据来源、状态含义 | 说明"数据口径" |
| 7. 系统边界与外部依赖 | 上下游系统、依赖关系 | 说明"系统边界" |
| 8. 非功能要求 | 性能、安全、兼容性等 | 说明"质量要求" |
| 9. 验收标准 | 可观察和可测试的验收项 | 说明"如何验收" |
| 10. 待确认问题 | 未解决的问题 | 说明"遗留问题" |

#### 2.2 需求覆盖规则

**核心规则**: 范围内的每个需求 ID 必须出现在 PRD 中，或在 `范围外` 中附带原因。

**示例**:
- ✅ FUNC-001 出现在"功能范围 - 范围内"
- ✅ FUNC-002 出现在"功能范围 - 范围外"，原因："业务方明确暂不做"
- ❌ FUNC-003 没有出现在 PRD 中（违反规则）

#### 2.3 前端需求处理

**规则**: 每个范围内的 `UI-*` 需求必须出现在用户角色/场景、功能范围、流程和验收标准中。

**示例**:
```markdown
## 2. 用户角色与场景
| 角色 | 场景 | 目标 | 关联需求 ID |
|------|------|------|-------------|
| 普通用户 | 访问注册页面 | 完成账号注册 | UI-001 |

## 3. 功能范围 - 范围内
| 功能 | 说明 | 关联需求 ID |
|------|------|-------------|
| 注册页面 | 白色背景，顶部标题，中部表单 | UI-001 |

## 9. 验收标准
| 验收项 | 通过标准 | 关联需求 ID |
|--------|----------|-------------|
| 注册页面 UI | 页面与设计稿一致，包含手机号输入框和验证码按钮 | UI-001 |
```

**禁止事项**: 除非 `requirements-register.md` 明确排除前端，否则不要将前端范围移到 `范围外`。

### 3. 验收标准设计

验收标准是 PRD 的核心产出，必须满足：

- ✅ **可观察**: 可以通过外部行为观察到
- ✅ **可测试**: 可以设计测试用例验证
- ✅ **有源需求 ID**: 追溯到源需求
- ✅ **具体**: 不是模糊的描述

**好示例**:
```markdown
| 验收项 | 通过标准 | 关联需求 ID |
|--------|----------|-------------|
| 用户注册 | 用户输入手机号和验证码后，点击注册按钮，系统创建用户并跳转到登录页 | FUNC-001, RULE-001 |
| 手机号验证 | 验证码错误时，显示"验证码错误"提示，不创建用户 | RULE-001 |
| 注册页面 UI | 页面与设计稿一致，包含手机号输入框和验证码按钮，背景为白色 | UI-001 |
```

**坏示例**:
```markdown
| 验收项 | 通过标准 | 关联需求 ID |
|--------|----------|-------------|
| 用户注册 | 功能正常 | FUNC-001 |  ❌ 不具体
| 性能要求 | 性能好 | NFR-001 |  ❌ 不可测试
| 页面美观 | 简洁美观 | UI-001 |  ❌ 不可观察
```

### 4. 质量门禁

返回前必须验证的 8 项要求：

| 验证项 | 说明 | 检查方法 |
|--------|------|----------|
| 源需求 ID 覆盖 | 范围内的每个需求 ID 都出现在 PRD 中 | 检查需求登记表与 PRD |
| 业务目标体现 | 业务目标、范围、流程、规则等已体现 | 检查 PRD 章节 |
| 验收标准具体 | 验收标准足够具体，可以供给验收场景生成 | 检查验收标准 |
| 验收标准有引用 | 每个验收标准都有稳定引用和源需求 ID | 检查验收标准表 |
| UI 需求覆盖 | 每个范围内的 UI-* 需求都有 PRD 覆盖和至少一个可观察的验收标准 | 检查 UI 需求 |
| 前端范围未静默移除 | 没有前端范围被静默移到 `范围外` | 检查范围外列表 |
| 阻断性问题已解决 | 没有 PRD 阻断性问题仍未解决 | 检查待确认问题 |
| 无编造需求 | 没有编造不受支持的需求 | 检查需求来源 |

### 5. 执行流程

```
读取 requirements-register.md
    ↓
读取项目入口文档
    ↓
提取业务目标、范围、流程、规则等
    ↓
生成 PRD 章节
    ↓
检查需求覆盖（每个需求 ID 都出现）
    ↓
检查 UI 需求覆盖（每个 UI-* 都有 PRD 覆盖）
    ↓
检查验收标准（可观察、可测试、有源需求 ID）
    ↓
检查阻断性问题
    ↓
质量门禁通过？──NO──→ 修复问题
    │
    YES
    ↓
写入 prd.md
    ↓
返回 STEP_RESULT (passed/blocked/failed)
```

### 6. 使用示例

#### 6.1 输入示例（requirements-register.md）

```markdown
## 源需求登记

| 需求 ID | 类型 | 原文摘录 | 结构化表述 |
|---------|------|----------|------------|
| BR-001 | BR | "我们需要一个用户管理功能" | 提供用户注册、登录和管理能力 |
| FUNC-001 | FUNC | "用户可以注册和登录" | 支持用户注册和登录功能 |
| RULE-001 | RULE | "注册需要手机号验证" | 注册时必须验证手机号 |
| UI-001 | UI | 视觉观察 | 注册页面白色背景，顶部标题，中部表单 |
| NFR-001 | NFR | "性能要好，支持高并发" | 注册登录接口支持高并发，响应时间<500ms |
```

#### 6.2 输出示例（prd.md）

```markdown

## 1. 背景与目标

- 业务背景：当前系统缺少用户管理能力，需要支持用户注册、登录和管理
- 目标：提供用户注册、登录和管理能力
- 成功标准：用户可以顺利完成注册和登录，管理员可以管理用户
- 关联需求 ID：BR-001

## 2. 用户角色与场景

| 角色 | 场景 | 目标 | 关联需求 ID |
|------|------|------|-------------|
| 普通用户 | 访问注册页面 | 完成账号注册 | UI-001 |
| 普通用户 | 登录系统 | 访问系统功能 | FUNC-001 |
| 管理员 | 管理用户 | 查看、编辑、删除用户 | FUNC-002 |

## 3. 功能范围

### 范围内

| 功能 | 说明 | 关联需求 ID |
|------|------|-------------|
| 用户注册 | 支持手机号注册，需要验证码验证 | FUNC-001, RULE-001 |
| 用户登录 | 支持手机号密码登录 | FUNC-001 |
| 用户管理 | 管理员可以查看、编辑、删除用户 | FUNC-002 |
| 注册页面 | 白色背景，顶部标题，中部表单 | UI-001 |

### 范围外

| 项目 | 原因 | 关联需求 ID |
|------|------|-------------|
| 用户权限管理 | 业务方明确暂不做 | BR-001 |
| 用户分组 | 业务方明确暂不做 | BR-001 |

## 4. 业务流程

### 主流程
1. 用户访问注册页面
2. 输入手机号和验证码
3. 点击注册按钮
4. 系统验证手机号和验证码
5. 验证通过，创建用户
6. 跳转到登录页

### 异常流程
1. 验证码错误 → 显示"验证码错误"提示，不创建用户
2. 手机号已注册 → 显示"手机号已注册"提示，不创建用户

### 边界流程
1. 验证码超时 → 显示"验证码已过期"提示，需要重新获取
2. 网络异常 → 显示"网络异常"提示，支持重试

## 5. 业务规则

| 规则 | 说明 | 关联需求 ID |
|------|------|-------------|
| 手机号格式 | 手机号必须为 11 位数字 | RULE-001 |
| 验证码有效期 | 验证码有效期为 5 分钟 | RULE-001 |
| 验证码重试 | 验证码最多重试 3 次 | RULE-001 |

## 6. 字段、数据与状态口径

| 项目 | 口径 | 来源 | 关联需求 ID |
|------|------|------|-------------|
| 手机号 | 11 位数字，以 1 开头 | 中国移动规范 | RULE-001 |
| 验证码 | 6 位数字 | 系统生成 | RULE-001 |
| 用户状态 | 0-未激活，1-已激活，2-已禁用 | 系统定义 | FUNC-001 |

## 7. 系统边界与外部依赖

| 系统或依赖 | 关系 | 输入/输出 | 风险 | 关联需求 ID |
|------------|------|-----------|------|-------------|
| 短信服务 | 上游 | 发送验证码 | 短信服务不可用时无法注册 | RULE-001 |
| 用户数据库 | 下游 | 存储用户数据 | 数据库故障时无法创建用户 | FUNC-001 |

## 8. 非功能要求

| 类型 | 要求 | 验收提示 | 关联需求 ID |
|------|------|----------|-------------|
| 性能 | 注册登录接口响应时间<500ms | 压力测试，并发 1000，响应时间<500ms | NFR-001 |

## 9. 验收标准

| 验收项 | 通过标准 | 关联需求 ID |
|--------|----------|-------------|
| 用户注册 | 用户输入手机号和验证码后，点击注册按钮，系统创建用户并跳转到登录页 | FUNC-001, RULE-001 |
```

### 9. 常见问题

#### Q1: PRD 可以包含技术设计吗？

**答**: 不可以。PRD 保留业务含义，不转为技术设计。例如：
- ✅ 业务描述："用户输入手机号和验证码后，系统创建用户"
- ❌ 技术设计："Controller 接收请求，Service 调用 Repository 保存用户"

#### Q2: 如何处理范围外的需求？

**答**: 在"范围外"章节中列出，并附带原因。例如：
```markdown
| 项目 | 原因 | 关联需求 ID |
|------|------|-------------|
| 用户权限管理 | 业务方明确暂不做 | BR-001 |
```

#### Q3: 验收标准不够具体怎么办？

**答**: 补充具体描述，使其可观察和可测试。例如：
- ❌ "功能正常"
- ✅ "用户输入手机号和验证码后，点击注册按钮，系统创建用户并跳转到登录页"

### 10. 适用场景

✅ **适合使用 prd 的场景**:
- 已有源需求登记（requirements-register.md）
- 需要产品需求文档的项目
- 需要明确功能范围和验收标准

❌ **不适合使用 prd 的场景**:
- 没有源需求登记
- 简单的文档更新（无需 PRD）
- 紧急热修复（流程过于冗长）

### 11. 限制与约束

- **唯一产物**: 只创建 `prd.md`，不创建其他文件
- **不创建下游产物**: 不创建 user-stories.md、design.md 等
- **不开始实现**: 不开始实现、测试、Git 或发布
- **保留业务含义**: 不转为技术设计

### 12. 总结

**4p12s-prd** 是 4P12S 技能体系的产品文档生成器，负责将结构化的源需求转换为人类可读的产品需求文档。它通过需求覆盖规则、验收标准设计和前端需求处理，确保 PRD 完整、可测试、可追溯。

**关键价值**:
- 业务翻译：将结构化的需求条目翻译为连贯的产品文档
- 范围界定：明确功能范围内和范围外的内容
- 流程定义：描述主流程、异常流程和边界流程
- 验收标准：定义可观察和可测试的验收标准
