# 4p12s-requirements 技能分析

## 基本信息

- **技能名称**: 4p12s-requirements
- **技能定位**: 需求访谈与登记
- **版本**: v1.0.3
- **文件路径**: `docs/skills/02-requirements.md`

---

## 原文核心内容

### 概述

将原始业务输入转换为交付流程的源需求登记。包含两个阶段：

1. **需求登记**：提取、分类、分配稳定 ID
2. **需求澄清**：对阻断 PRD 生成的问题向用户提问，持续处理直到足以支撑 PRD

### 双模运行

#### 编排模式（被 4p12s-delivery-orchestrator 调用）

接收路径包，读取其中的输入文件，写入指定的输出路径，返回 `STEP_RESULT`。

路径包必须包含：

```yaml
repo_root:
delivery_dir:
state_path:
project_entry_path:
raw_input_path:          # 原始业务输入路径或文本
requirements_register_path:  # 已存在的 requirements-register.md 路径（更新场景）
output_paths:
allowed_write_paths:     # 仅 requirements-register.md
```

#### 独立模式（用户直接调用）

用户直接提供业务需求（文本、文件路径、截图等）。Skill 自动发现：

- 当前项目根目录（`git rev-parse --show-toplevel` 或当前目录）
- 项目入口文档（`.gientech/AGENTS.md`、`AGENTS.md`、`README.md`）
- 输出路径：`deliveries/<需求名>/requirements-register.md`（如用户未指定）

独立模式直接面向用户输出 `requirements-register.md`，不需要返回 `STEP_RESULT`。

### 输出文件

写入唯一产物：`requirements-register.md`

```markdown

## 需求总览

- 业务目标：
- 成功标准：
- 范围内：
- 范围外：

## 源需求登记

| 需求 ID | 类型 | 来源位置 | 原文摘录或视觉观察 | 结构化表述 | 优先级 | 验收提示 | 当前状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |

## 澄清问题

| 问题 ID | 关联需求 ID | 问题 | 影响 | 是否阻断后续 PRD | 询问方式 |
```

### 需求 ID 规则

按需求类型分配稳定 ID：

- `BR-001`：业务背景、目标或成功标准
- `FUNC-001`：功能能力
- `RULE-001`：业务规则、校验、风控或策略
- `FLOW-001`：流程、状态流、正常路径、异常路径或边界路径
- `FIELD-001`：字段、数据源、数据含义或数据质量规则
- `UI-001`：页面结构、布局、控件、交互状态、视觉风格、截图证据或图片中可见的现有系统行为
- `PERM-001`：角色、权限、授权、审计或合规规则
- `NFR-001`：性能、安全、兼容性、可观测性、可用性或运维要求
- `INT-001`：上下游系统、API、事件、批处理、文件或外部依赖

已有登记中已有 ID 不得重新编号。同一前缀的新 ID 追加在当前最大编号之后。

### 提取规则

- 始终保留输出结构中的所有固定章节
- 保留原始业务含义，不将业务请求翻译为技术方案
- 对于图片/截图/设计稿/扫描件，先记录视觉观察作为证据，再映射到稳定需求 ID
- 当源描述涉及用户可见界面、页面/表单、字段、交互、输入/输出时，创建 `UI-*` 需求
- 不要将前端交互信号降级为仅 `NFR-*`
- 图片模糊、置信度低或与文本冲突时，创建澄清问题而非猜测
- 当复合需求有不同的验收信号、负责人、系统或风险时，进行拆分
- 将业务规则、数据规则、权限、异常路径和非功能需求作为独立行保留
- 澄清问题 ID（`Q-001`）是证据 ID，不是源需求 ID
- 仅当调用方或源明确排除时才标记 `暂不做`
- 不要编造优先级，缺失时使用 `未明确`

### 澄清流程

登记完成后，检查是否存在阻断 PRD 生成的澄清项：

1. 找到标记为阻断的澄清项，按影响合并为最少必要问题
2. 直接向用户提出澄清问题
3. 用户回答后，更新相关需求行、澄清行和验收提示
4. 保留原始源描述，将澄清答案作为补充证据记录
5. 重新审计是否还有阻断性澄清项
6. 仅在没有阻断性澄清项、用户明确无法提供关键答案时结束

**澄清边界**：
- 不提出设计、实现、测试、Git 或发布问题
- 不提出多种产品方案，除非源需求本身歧义且答案对 PRD 语义是必需的
- 不创建下游产物
- 不删除原始需求文本
- 如果答案改变了范围，记录范围决策和受影响的需求 ID
- 非阻断性澄清项也必须有处置结论

### 质量门禁

返回前验证：

- `requirements-register.md` 包含所有固定章节，包括 `视觉证据登记`
- 范围内的每个业务事实都有稳定的源需求 ID
- 每个澄清项都有阻断标志和下一步动作
- 非阻断性澄清项有下游阶段可引用的处置记录
- 每个文本或图片前端信号都映射到 `UI-*`，或有源/调用方证据明确排除
- 没有前端交互信号被仅降级为 `NFR-*`、风格描述或人工验收措辞
- 文件中没有出现下游专属 US、AC、SC、TC、Task、设计、实现、Git 或发布结论
- 澄清 ID 未替代源需求 ID

### STEP_RESULT（编排模式）

```yaml
step: requirements
status: running | passed | blocked | failed
output_files:
  - <delivery_dir>/requirements-register.md
required_inputs_checked:
  - <project_entry_path>
  - <raw_input_path_or_inline_text>
commands_run: none
gate_evidence:
blocking_reason:
next_action:
```

- `passed`：登记有足够证据支撑 PRD 生成
- `blocked`：存在阻断 PRD 生成的澄清问题且用户无法提供答案，或需要外部业务决策

### 边界

- 不创建 `prd.md`、`user-stories.md`、`design.md`、`tasks/`、`verification-plan.md`、`verification-result.md` 或 `deploy-log.md`
- 不开始实现、测试、Git 或发布

### 更新 delivery-state.md（仅独立运行模式）

> **编排模式**（被 `4p12s-delivery-orchestrator` 调用）下，`delivery-state.md` 由 orchestrator 统一处理，本 Skill **不直接更新**。

仅在**独立运行模式**（用户直接调用本 Skill）下，本 Step 完成后（或 `failed` / `blocked` 时）必须更新 `<state_path>`：

1. `## Step Checklist` 表中当前 Step 对应行的 `Status` 改为 `passed` / `failed` / `blocked`；`Evidence` 列填入产物文件路径（多文件用 `；` 分隔）
2. 顶部字段：`current_step` 设为下一 Step（`passed` 时）或保持当前 Step（`failed` / `blocked` 时）；`next_action` 设为对下一/当前 Step 的提示；`blocked` / `failed` 时填写 `blocking_reason`；`updated_at` 改为当前 ISO8601 时间戳
3. 不修改其他 Step / Task 的状态

## 分析说明

### 1. 设计意图

**4p12s-requirements** 是 4P12S 技能体系的**需求入口**，负责将原始业务输入转换为结构化的源需求登记。它的核心价值在于：

- **需求结构化**: 将模糊的业务描述转换为结构化的需求条目
- **稳定 ID 追溯**: 为每个需求分配稳定的 ID，作为下游追溯的源头
- **需求澄清**: 识别并解决需求歧义，确保足以支撑 PRD 生成
- **视觉证据**: 对图片/截图等视觉输入进行证据登记

这种设计的优势：
1. **可追溯性**: 下游产物可以追溯到源需求 ID
2. **需求完整性**: 通过澄清流程确保需求完整无歧义
3. **视觉证据**: 对截图等视觉输入进行规范化处理
4. **前后端分离**: 明确区分前端交互需求和后端功能需求

### 2. 核心概念解析

#### 2.1 需求 ID 系统（9 种类型）

需求 ID 系统是需求追溯的基础，共 9 种类型：

| 前缀 | 类型 | 说明 | 示例 |
|------|------|------|------|
| `BR-xxx` | Business Requirement | 业务背景、目标、成功标准 | BR-001: 提升用户注册转化率 |
| `FUNC-xxx` | Function | 功能能力 | FUNC-001: 支持手机号注册 |
| `RULE-xxx` | Rule | 业务规则、校验、风控策略 | RULE-001: 手机号必须验证 |
| `FLOW-xxx` | Flow | 流程、状态流、异常路径 | FLOW-001: 注册流程包含 3 步 |
| `FIELD-xxx` | Field | 字段、数据源、数据含义 | FIELD-001: 手机号字段格式 |
| `UI-xxx` | User Interface | 页面结构、交互、视觉风格 | UI-001: 注册页面布局 |
| `PERM-xxx` | Permission | 角色、权限、合规规则 | PERM-001: 管理员可查看所有用户 |
| `NFR-xxx` | Non-Functional Requirement | 性能、安全、兼容性 | NFR-001: 注册接口响应<500ms |
| `INT-xxx` | Integration | 上下游系统、API、事件 | INT-001: 对接短信服务 |

**关键点**:
- 已有 ID 不得重新编号
- 同一前缀的新 ID 追加在当前最大编号之后
- 澄清问题 ID（`Q-xxx`）不是源需求 ID

#### 2.2 视觉证据登记

对于图片/截图/设计稿/扫描件等视觉输入，需要登记：

| 字段 | 说明 |
|------|------|
| `image_id` | 图片唯一标识 |
| `图片路径或附件名` | 图片文件位置 |
| `区域位置` | 图片中的具体区域（如"顶部导航栏"） |
| `视觉观察` | 客观描述看到的内容 |
| `提取出的需求 ID` | 映射到的需求 ID（如 UI-001） |
| `置信度` | 高/中/低 |
| `未解决问题` | 需要澄清的问题 |

**示例**:
```markdown
| image_id | 图片路径 | 区域位置 | 视觉观察 | 需求 ID | 置信度 | 未解决问题 |
|----------|----------|----------|----------|---------|--------|------------|
| img-001 | screenshots/register.png | 顶部表单 | 蓝色背景，包含手机号输入框和验证码按钮 | UI-001 | 高 | 无 |
```

#### 2.3 需求提取规则

**核心规则**:

1. **保留原始业务含义**: 不将业务请求翻译为技术方案
   - ✅ 原文："用户需要快速注册"
   - ❌ 翻译："需要添加 Redis 缓存"

2. **前端信号映射到 UI-***: 涉及页面/表单/交互时，创建 UI 需求
   - ✅ "注册页面需要手机号输入框" → UI-001
   - ❌ 降级为 NFR-001: "注册接口性能要求"

3. **图片处理**: 先记录视觉观察，再映射到需求 ID
   - ✅ 视觉观察："蓝色按钮，文字为'立即注册'"
   - ❌ 直接猜测："按钮颜色为#409EFF"

4. **需求拆分**: 复合需求有不同验收信号时拆分
   - ✅ "注册后发送邮件和短信" → FUNC-001 + FUNC-002
   - ❌ 合并为一条需求

5. **澄清问题 ID**: `Q-xxx` 是证据 ID，不是源需求 ID
   - ✅ Q-001 关联 FUNC-001
   - ❌ 用 Q-001 替代 FUNC-001

### 3. 澄清流程

```
登记完成
    ↓
检查阻断 PRD 的澄清项
    ↓
合并为最少必要问题
    ↓
向用户提问
    ↓
用户回答
    ↓
更新需求行、澄清行、验收提示
    ↓
重新审计
    ↓
还有阻断项？──YES──┘
    │
    NO
    ↓
结束（passed 或 blocked）
```

**澄清边界**（什么该问，什么不该问）:

- ✅ **该问的**:
  - 需求歧义影响 PRD 语义
  - 范围不明确
  - 关键业务规则缺失
  - 前端交互细节模糊

- ❌ **不该问的**:
  - 设计、实现、测试、Git 或发布问题
  - 多种产品方案选择（除非源需求本身歧义）
  - 非阻断性问题（可以记录但不提问）

### 4. 质量门禁

返回前必须验证的 8 项要求：

| 验证项 | 说明 | 检查方法 |
|--------|------|----------|
| 固定章节完整 | 包含所有固定章节，包括 `视觉证据登记` | 检查 Markdown 结构 |
| 需求 ID 覆盖 | 范围内的每个业务事实都有稳定的源需求 ID | 检查需求登记表 |
| 澄清项完整 | 每个澄清项都有阻断标志和下一步动作 | 检查澄清问题表 |
| 非阻断项处置 | 非阻断性澄清项有下游阶段可引用的处置记录 | 检查处置记录 |
| 前端信号映射 | 每个文本或图片前端信号都映射到 `UI-*` | 检查 UI 需求 |
| 前端信号未降级 | 没有前端交互信号被仅降级为 `NFR-*` | 检查需求类型 |
| 无下游内容 | 文件中没有出现下游专属 US、AC、SC、TC 等 | 检查文件内容 |
| 澄清 ID 未替代 | 澄清 ID 未替代源需求 ID | 检查 ID 引用 |

### 5. 执行流程

```
接收原始业务输入
    ↓
读取项目入口文档
    ↓
提取需求（9 种类型）
    ↓
分配稳定 ID
    ↓
登记视觉证据（如有图片）
    ↓
检查阻断 PRD 的澄清项
    ↓
有阻断项？──YES──→ 向用户提问 ──→ 用户回答 ──→ 更新需求
    │                                            │
    NO                                           │
    ↓                                            └──────┘
检查质量门禁
    ↓
门禁通过？──NO──→ 修复问题
    │
    YES
    ↓
返回 STEP_RESULT (passed/blocked/failed)
```

### 6. 使用示例

#### 6.1 输入示例

用户提供业务需求：

```
我们需要一个用户管理功能，包括：
1. 用户可以注册和登录
2. 管理员可以管理用户
3. 注册需要手机号验证
4. 登录页面要简洁美观
5. 性能要好，支持高并发

截图：screenshots/register.png
```

#### 6.2 输出示例（requirements-register.md）

```markdown
# 用户管理功能 源需求登记

## 输入来源

| 来源 | 位置 | 说明 |
| --- | --- | --- |
| 用户输入 | 对话文本 | 业务需求描述 |
| 截图 | screenshots/register.png | 注册页面设计稿 |

## 视觉证据登记

| image_id | 图片路径 | 区域位置 | 视觉观察 | 需求 ID | 置信度 | 未解决问题 |
| --- | --- | --- | --- | --- | --- | --- |
| img-001 | screenshots/register.png | 整体布局 | 白色背景，顶部标题"用户注册"，中部表单区域 | UI-001 | 高 | 无 |

## 需求总览

- 业务目标：提供用户注册、登录和管理能力
- 成功标准：用户可以顺利完成注册和登录，管理员可以管理用户
- 范围内：用户注册、用户登录、用户管理
- 范围外：用户权限管理、用户分组

## 源需求登记

| 需求 ID | 类型 | 来源位置 | 原文摘录 | 结构化表述 | 优先级 | 验收提示 | 当前状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| BR-001 | BR | 用户输入 | "我们需要一个用户管理功能" | 提供用户注册、登录和管理能力 | 高 | 用户可完成注册登录 | 已接受 |
| FUNC-001 | FUNC | 用户输入 | "用户可以注册和登录" | 支持用户注册和登录功能 | 高 | 注册登录流程可用 | 已接受 |
| FUNC-002 | FUNC | 用户输入 | "管理员可以管理用户" | 管理员可以查看、编辑、删除用户 | 高 | 管理员功能可用 | 已接受 |
| RULE-001 | RULE | 用户输入 | "注册需要手机号验证" | 注册时必须验证手机号 | 高 | 手机号验证通过才能注册 | 已接受 |
| UI-001 | UI | 截图 | 视觉观察 | 注册页面白色背景，顶部标题，中部表单 | 中 | 页面与设计稿一致 | 已接受 |
| NFR-001 | NFR | 用户输入 | "性能要好，支持高并发" | 注册登录接口支持高并发，响应时间<500ms | 高 | 压力测试通过 | 已接受 |

## 澄清问题

| 问题 ID | 关联需求 ID | 问题 | 影响 | 是否阻断后续 PRD | 询问方式 |
| --- | --- | --- | --- | --- | --- |
| Q-001 | FUNC-002 | 管理员具体可以管理用户的哪些信息？ | 影响 PRD 中功能范围定义 | 是 | 直接提问 |

## 范围与风险

| 事项 | 关联需求 ID | 说明 | 下一步动作 |
| --- | --- | --- | --- |
| 用户权限管理 | BR-001 | 暂不包含权限管理功能 | 记录在范围外 |
| 手机号验证服务 | RULE-001 | 依赖外部短信服务 | 需要在设计阶段确认对接方案 |
```

### 7. 与其他技能的关系

```
原始业务输入
    ↓
4p12s-requirements
    ↓
requirements-register.md (源需求登记)
    ↓
4p12s-prd
    ↓
prd.md (产品需求文档)
```

**关键点**:
- requirements 是需求追溯的源头
- 所有下游产物都可以追溯到源需求 ID
- 需求澄清在 requirements 阶段完成，PRD 阶段不再提问

#### 8.3 需求澄清

- ✅ 合并阻断项为最少必要问题
- ✅ 用户回答后更新需求行和澄清行
- ❌ 不要提出设计、实现、测试问题

### 9. 常见问题

#### Q1: 如何判断需求是否阻断 PRD 生成？

**答**: 判断标准：
- 需求描述模糊，无法确定功能范围
- 关键业务规则缺失
- 前端交互细节不明确
- 范围不明确（范围内/范围外）

例如："管理员可以管理用户" 没有说明具体管理哪些信息，属于阻断项。

#### Q2: 前端交互需求可以降级为 NFR 吗？

**答**: 不可以。前端交互信号必须映射到 UI-*，不能降级为 NFR-*。例如：
- ✅ "注册页面要简洁美观" → UI-001
- ❌ "注册页面要简洁美观" → NFR-001（可用性要求）

#### Q3: 澄清问题 ID 可以替代源需求 ID 吗？

**答**: 不可以。澄清问题 ID（Q-xxx）只是证据 ID，不是源需求 ID。例如：
- ✅ Q-001 关联 FUNC-001
- ❌ 用 Q-001 替代 FUNC-001

### 10. 适用场景

✅ **适合使用 requirements 的场景**:
- 从原始业务输入开始的需求分析
- 需要需求追溯的项目
- 有图片/截图等视觉输入的场景
- 需求不明确需要澄清的场景

❌ **不适合使用 requirements 的场景**:
- 已有明确 PRD 的项目
- 简单的文档更新（无需需求分析）
- 紧急热修复（流程过于冗长）

### 11. 限制与约束

- **唯一产物**: 只创建 `requirements-register.md`，不创建其他文件
- **不创建下游产物**: 不创建 prd.md、user-stories.md 等
- **不开始实现**: 不开始实现、测试、Git 或发布
- **澄清边界**: 不提出设计、实现、测试、Git 或发布问题

### 12. 总结

**4p12s-requirements** 是 4P12S 技能体系的需求入口，负责将原始业务输入转换为结构化的源需求登记。它通过稳定 ID 系统、视觉证据登记和需求澄清流程，确保需求完整、无歧义，为下游产物提供可追溯的源头。

**关键价值**:
- 需求结构化：将模糊的业务描述转换为结构化的需求条目
- 稳定 ID 追溯：为每个需求分配稳定的 ID，作为下游追溯的源头
- 需求澄清：识别并解决需求歧义，确保足以支撑 PRD 生成
- 视觉证据：对图片/截图等视觉输入进行证据登记
