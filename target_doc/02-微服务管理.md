# 开发平台需求文档 - 微服务管理

## 1. 模块概述

微服务隶属于应用，是模型、服务、服务编排的归属容器。一个应用对应多个微服务，每个微服务代表应用内一个独立的业务边界或能力域。

微服务管理模块负责微服务的创建、维护、查询与生命周期管理，并提供微服务下各类研发资产的统一查看入口。

## 2. 核心概念

- **微服务**：应用内独立的业务单元，下辖模型、服务、编排。
- **微服务编码**：微服务在所属应用内的唯一标识。
- **微服务状态**：微服务的生命周期状态（启用/停用）。

## 3. 功能需求

### 3.1 微服务基本信息维护

- 支持维护微服务的基本信息，包括但不限于：微服务名称、微服务编码、微服务描述、版本。
- 微服务编码在同一应用内唯一。

### 3.2 微服务创建/编辑/删除/查询

- **创建**：在指定应用下新建微服务，录入基本信息并保存。
- **编辑**：支持修改微服务的基本信息（微服务编码一经创建通常不允许修改）。
- **删除**：支持删除微服务，删除前需进行关联校验。
- **查询**：支持在应用下按名称、编码、状态等条件检索微服务列表，支持分页。

### 3.3 微服务状态管理

- 支持微服务的启用/停用操作。
- 停用微服务后，该微服务下的模型、服务、编排进入不可用状态（服务不可被编排调用）。

### 3.4 微服务下资源统一查看入口

- 在微服务详情中提供其下辖资源的统一查看入口，至少包括：
  - 微服务下的模型列表；
  - 微服务下的服务列表；
  - 微服务下的服务编排列表。
- 支持从微服务入口快速下钻到对应资源模块。

## 4. 业务规则

1. 微服务必须归属于某一应用，不存在无应用的微服务。
2. 同一应用内微服务编码唯一；不同应用间允许相同编码。
3. 删除微服务时需校验是否存在关联的模型、服务或编排：
   - 若存在关联资源，应阻止删除或要求先清理关联资源（建议默认阻止并提示）。
4. 停用微服务后，其下服务不可被服务编排调用，已有编排引用需告警。
5. 微服务编码一经创建不允许修改，以保证引用稳定性。

## 5. 与其他模块关联

- **微服务 1:N 模型**：一个微服务下可定义多个模型，模型必须归属于某一微服务。详见 [03-模型管理](03-模型管理.md)。
- **微服务 1:N 服务**：一个微服务下可定义多个服务，服务必须归属于某一微服务。详见 [05-服务管理](05-服务管理.md)。
- **服务编排归属微服务**：一个服务编排归属于一个微服务，但可跨微服务调用服务。详见 [06-服务编排](06-服务编排.md)。
- **向上关联**：微服务归属于应用。详见 [01-应用管理](01-应用管理.md)。
