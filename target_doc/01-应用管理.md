# 开发平台需求文档 - 应用管理

## 1. 模块概述

应用是平台最高层级的管理对象，是微服务与元数据的归属容器。一个应用对应一个完整的业务系统，其下所有的微服务、元数据、模型、服务、编排均归属于该应用。

应用管理模块负责应用的创建、维护、查询与生命周期管理，并提供应用下各类研发资产的统一查看入口。

## 2. 核心概念

- **应用**：平台顶层研发资产容器，下辖微服务与元数据。
- **应用编码**：应用在平台中的唯一标识，用于系统级引用。
- **应用状态**：应用的生命周期状态（启用/停用），控制应用下资源是否可用。

## 3. 功能需求

### 3.1 应用基本信息维护

- 支持维护应用的基本信息，包括但不限于：应用名称、应用编码、应用描述、版本。
- 应用编码在平台内全局唯一，用于系统级标识与引用。

### 3.2 应用创建/编辑/删除/查询

- **创建**：支持新建应用，录入基本信息并保存。
- **编辑**：支持修改应用的基本信息（应用编码一经创建通常不允许修改，需明确约束）。
- **删除**：支持删除应用，删除前需进行关联校验。
- **查询**：支持按名称、编码、状态等条件检索应用列表，支持分页。

### 3.3 应用状态管理

- 支持应用的启用/停用操作。
- 停用应用后，该应用下的微服务、元数据等资源应进入不可用状态（不可被引用、不可参与编排调用）。

### 3.4 应用下资源统一查看入口

- 在应用详情中提供其下辖资源的统一查看入口，至少包括：
  - 应用下的微服务列表；
  - 应用下的元数据列表。
- 支持从应用入口快速下钻到对应资源模块。

### 3.5 应用导入/导出

- 支持应用的导出，将应用及其关联资源（微服务、元数据等）结构化导出，便于备份与迁移。
- 支持应用的导入，可基于导出的结构化数据在平台中还原应用资产。

## 4. 业务规则

1. 应用编码在平台内全局唯一。
2. 应用名称允许重复，但建议在展示层加以区分。
3. 删除应用时需校验是否存在关联的微服务或元数据：
   - 若存在关联资源，应阻止删除或要求先清理关联资源（需明确策略，建议默认阻止并提示）。
4. 停用应用后，其下所有资源进入不可用状态，已有的引用关系（如跨应用引用）需相应告警或失效。
5. 应用编码一经创建不允许修改，以保证引用稳定性（若允许修改需同步处理所有引用）。

## 5. 与其他模块关联

- **应用 1:N 微服务**：一个应用下可包含多个微服务，微服务必须归属于某一应用。详见 [02-微服务管理](02-微服务管理.md)。
- **应用 1:N 元数据**：一个应用下可定义多个元数据，元数据必须归属于某一应用。详见 [04-元数据管理](04-元数据管理.md)。
