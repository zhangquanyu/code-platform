# 模块详细设计 - 服务编排

## 1. 概述

服务编排隶属于某微服务，但可跨微服务调用；以流程图画布方式组织节点与连线。对应数据库表 `dev_orchestration`、`dev_orch_node`、`dev_orch_edge`。

## 2. 前端界面设计

### 2.1 页面清单

| 路由 | 页面 |
| --- | --- |
| `/orchestrations` | 编排列表页 |
| `/orchestrations/create` | 新建编排（基本信息） |
| `/orchestrations/:id` | 编排详情页 — 流程画布 + 入参/出参 + 调试 |

### 2.2 编排列表页

- 搜索：应用、微服务、关键字（名称/编码）、状态。
- 表格：名称、编码、所属微服务、节点数、连线数、状态、创建时间、操作。
- 「新建编排」按钮。

### 2.3 新建编排（第一步）

表单：所属微服务 `*`、名称 `*`、编码 `*`、描述。

### 2.4 编排详情页（核心：流程画布）

**布局：**
```

│                                     │                           │

│ 选中节点 →                          │                           │
```

### 2.5 编排画布交互要点

- 拖拽节点到画布，自动生成 `node_key`（前端 UUID）。
- 从节点右侧锚点拖线到下一节点左侧锚点生成连线（edge）。
- 选中节点 → 右侧面板展示对应属性；未选中展示编排整体信息。
- 保存前自动执行校验：缺失开始/结束节点；SERVICE 未选服务；CONDITION 未写表达式；节点悬空。
- 校验结果定位：点击错误跳转到对应节点并高亮。

### 2.6 调试面板

- 顶部「执行一次」按钮：弹出编排入参表单（按定义的入参 + 类型）。
- 执行完成后：流程图标注每个节点执行耗时与状态（成功/失败）；底部日志面板查看节点输入输出 JSON。
- 失败节点高亮并展开错误堆栈信息。

## 3. 后端接口设计

**Base：** `/api/v1/orchestrations`

### 3.1 分页查询编排列表

- **GET** `/api/v1/orchestrations`
- **Query：** pageNum, pageSize, keyword, microserviceId, applicationId, status
- **响应：** `PageResult<OrchestrationVO>`
  ```ts
  interface OrchestrationVO {
    id: number
    microserviceId: number
    microserviceName: string
    applicationId: number
    name: string
    code: string
    description: string | null
    status: 0 | 1
    nodeCount: number
    edgeCount: number
    createTime: string
  }
  ```

### 3.2 编排详情（画布完整数据）

- **GET** `/api/v1/orchestrations/{id}`
- **响应：**
  ```json
  {
    "orchestration": { "id": 1, "name": "下单流程", "code": "placeOrder", "..." : "..." },
    "inputParams": [
      { "paramName": "userId", "dataType": "BIGINT", "isRequired": true, "paramComment": "下单用户ID" }
    ],
    "outputParams": [
      { "paramName": "orderNo", "dataType": "TEXT", "paramComment": "订单号", "sourceNodeKey": "svc_1", "sourceField": "orderNo" }
    ],
    "nodes": [
      {
        "nodeKey": "start_1",
        "nodeType": "START",
        "nodeName": "开始",
        "serviceId": null,
        "configJson": null,
        "xPos": 50,
        "yPos": 120
      },
      {
        "nodeKey": "svc_1",
        "nodeType": "SERVICE",
        "nodeName": "创建订单",
        "serviceId": 3001,
        "configJson": {
          "mapping": {
            "userId": { "source": "INPUT", "key": "userId" },
            "itemList": { "source": "INPUT", "key": "items" }
          }
        },
        "xPos": 260, "yPos": 120
      }
    ],
    "edges": [
      { "edgeKey": "e1", "fromNodeKey": "start_1", "toNodeKey": "svc_1", "conditionExpr": null, "labelText": null }
    ]
  }
  ```

### 3.3 创建编排基本信息

- **POST** `/api/v1/orchestrations` → `{ microserviceId, name, code, description }`
- 创建返回空编排（无节点/连线/入参/出参）。

### 3.4 整体保存编排（画布+参数）

- **PUT** `/api/v1/orchestrations/{id}`
- **请求体：** 与 GET {id} 响应结构一致（`inputParams/outputParams/nodes/edges` 全量重写）。
- **服务端校验（保存即校验）：**
  1. 开始节点数量 = 1，结束节点 ≥ 1。
  2. SERVICE 节点 `serviceId` 必传且服务启用。
  3. CONDITION 节点至少两条出边（真/假），且 `conditionExpr` 非空。
  4. 所有 `fromNodeKey/toNodeKey` 均存在。
  5. 跨微服务校验：被调用服务微服务需存在且启用。
- 校验失败返回 65001 + 明细列表（定位到 nodeKey/edgeKey）。

### 3.5 单独校验（可选，供前端「校验」按钮）

- **POST** `/api/v1/orchestrations/{id}/validate`
- **请求体：** 同 PUT 的 nodes/edges 部分（允许未保存版本预校验）。

### 3.6 删除编排

- **DELETE** `/api/v1/orchestrations/{id}`

### 3.7 状态切换

- **PUT** `/api/v1/orchestrations/{id}/status` → `{ status }`

### 3.8 编排执行/调试

- **POST** `/api/v1/orchestrations/{id}/debug`
- **请求体：**
  ```json
  {
    "inputData": { "userId": 1001, "items": [{ "skuId": 1, "qty": 2 }] }
  }
  ```
- **响应：** 同步执行结果（或返回 debugId 异步查询）
  ```json
  {
    "success": true,
    "output": { "orderNo": "NO20260812001" },
    "nodeResults": [
      {
        "nodeKey": "svc_1",
        "nodeName": "创建订单",
        "status": "SUCCESS",
        "durationMs": 120,
        "input": { "...": "..." },
        "output": { "...": "..." },
        "error": null
      }
    ],
    "totalDurationMs": 150
  }
  ```

### 3.9 受影响服务告警（辅助接口）

- **GET** `/api/v1/orchestrations/{id}/health`
- 返回：该编排引用的所有服务是否「可用」。若某服务被删除或停用，返回告警列表（nodeKey + serviceId + 原因）。

## 4. 领域对象

### Entity

- `Orchestration`（id, microserviceId, name, code, description, status）
- `OrchestrationNode`（id, orchestrationId, nodeKey, nodeType, nodeName, serviceId, configJson[TEXT→JSON], xPos, yPos, sortOrder）
- `OrchestrationEdge`（id, orchestrationId, edgeKey, fromNodeKey, toNodeKey, conditionExpr, labelText）
- （可选）`OrchParam` 表存入参/出参；或直接将入参/出参以 JSON 存入 `Orchestration.inputs_json/outputs_json`。本期建议单独建表 `dev_orch_param` 以便校验与展示。

### DTO

- `OrchestrationCreateCmd` / `OrchestrationUpdateCmd`（整体保存体）
- `OrchestrationPageQuery`
- `OrchestrationVO` / `OrchestrationDetailVO`
- `OrchNodeVO` / `OrchEdgeVO` / `OrchParamVO`
- `OrchValidateCmd` / `OrchValidateResultVO`
- `OrchDebugCmd` / `OrchDebugResultVO`

## 5. 关键业务逻辑

1. **整体保存事务**：PUT 时以「先删后增」或「基于 node_key/edge_key 差异对比」的策略，保证 nodes 与 edges 一致性。推荐：
   - 按 orchestrationId 查询现有 nodes/edges；
   - 以 node_key 为主键做 upsert + 缺失 key 删除（软删）。
2. **跨微服务服务选择**：SERVICE 节点 serviceId 可指向任意微服务，但该微服务所属应用必须与编排所属微服务应用一致（本期不支持跨应用）。
3. **删除/停用告警**：服务被删除或停用后，`health` 接口立即返回告警，编排列表展示一个「异常」红点。
4. **调试模拟执行**：本期调试层可做「Mock 执行」（按服务出参 schema 生成 mock）或「真实 HTTP 转发调用」，两者选一，需在实现阶段明确（建议先 Mock，降低依赖）。
